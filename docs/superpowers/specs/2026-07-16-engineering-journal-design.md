# Enterprise Agentic RAG 工程记录与学习体系设计

日期：2026-07-16

状态：已获本人批准采用方案 C，等待书面规范复核

## 1. 背景

当前仓库已经有阶段设计、实施说明、data card、私有审计记录和学习卡。这些材料能够回答“最终做出了什么”，但还不能稳定回答下面这些问题：

- 每个行为变化修改前是什么状态；
- 为什么选择这个方案，而不是另外两个方案；
- 失败测试具体证明了什么；
- 哪个文件、函数和数据结构承担了变化；
- 调试过程中排除了哪些错误假设；
- 指标变好、没变或变坏分别说明什么；
- 哪些内容是当时保存的证据，哪些是阶段结束后回填的解释；
- 本人应该如何通过实验真正掌握这次修改。

因此需要一套可以持续用于 E0-E7 的记录体系，而不是只扩写一次 E1 总结。

## 2. 目标

记录体系必须同时服务三类读者：

1. 招聘者：快速确认项目问题、方案、代码、验证和边界。
2. 后续协作者：能够从稳定 ID 找到某项决策、故障和测试证据。
3. 项目本人：能够沿代码入口复现实验，并练习面试表达。

完成后，应能从任一阶段回答：

```text
为什么改
-> 改前证据是什么
-> 考虑了哪些方案
-> 实际改了哪些代码
-> 中途为什么失败
-> 最终如何验证
-> 结果为什么好或不好
-> 还不能证明什么
-> 面试时如何准确表达
```

### 2.1 初学者可读性要求

“详细”不能等同于堆更多术语。每个阶段文档必须允许读者按三种深度阅读：

1. **第一遍，只看白话摘要**：知道原来有什么问题、现在增加了什么、结果是否真的变好。
2. **第二遍，看数据流和代码导航**：知道请求或数据经过哪些文件、类和函数。
3. **第三遍，看关键代码与测试**：理解每个判断条件、异常分支和断言为什么存在。

每个 Change 开头必须包含“先说人话”，限制在 3-6 句话。遇到首次出现的术语时立即解释，不要求读者先懂 Pydantic、manifest、ACL、fixture、hash、atomic write 或 held-out test。

代码解释必须回答：

```text
输入是什么
-> 函数先检查什么
-> 中间状态怎么变化
-> 输出是什么
-> 哪些输入会失败
-> 失败时为什么不能继续
```

只写“新增了某个类/函数”不合格。必须解释这个类在完整数据流中的位置，以及删除它或写错它会出现什么用户可见问题。

## 3. 非目标

- 不把聊天内容逐字复制进仓库。
- 不为了显得过程完整而事后编造失败测试、命令输出或时间线。
- 不重复粘贴整段源代码；记录关键片段、接口和文件位置即可。
- 不把测试数量当作质量结论。
- 不自动把本人的学习状态改成“已掌握”。
- 不在公开仓库记录真实用户名、私人目录、Token、模型文件路径或求职材料内容。
- 不因写记录而放宽阶段门禁、自动 commit 或自动 push。

## 4. 方案选择

### 方案 A：只扩写阶段实施说明

优点是文件少。缺点是故障、设计决策和学习任务会混在同一篇长文中，跨阶段难以检索。

### 方案 B：单一时间线总日志

优点是按时间完整。缺点是 E2 之后文件会迅速膨胀，招聘者难以找到某个模块的因果链。

### 方案 C：三层记录，已批准

1. 仓库内阶段技术实施记录：解释问题、架构、代码和验证。
2. 跨阶段决策与故障总账：使用稳定 ID 索引关键选择和失败。
3. 私有学习卡与审计记录：保存本地命令、本人实验、面试训练和学习状态。

方案 C 将公开技术证据与私人学习材料分开，同时通过稳定 ID 避免重复叙述失去关联。

## 5. 文件架构

### 5.1 仓库公开记录

```text
docs/roadmap/e0_readonly_audit_implementation.md
docs/roadmap/e1_enterprise_corpus_implementation.md
docs/roadmap/e2_parser_index_lifecycle_implementation.md
docs/roadmap/engineering_decision_failure_ledger.md
docs/data_card.md
```

- `eX_*_implementation.md`：一个阶段的完整技术因果链。
- `engineering_decision_failure_ledger.md`：跨阶段索引，不复制完整实施说明。
- `data_card.md`：只描述数据本身，不承担工程过程日志职责。

后续 E3-E7 沿用相同命名规则。

### 5.2 私有记录

```text
<private-career-root>/审计与验收/Enterprise_Agentic_RAG_v2_Ex_实施记录.md
<private-career-root>/学习任务/RAG工业化升级/Ex_<阶段>_学习卡.md
```

- `<private-career-root>` 只在本地执行时解析为本人指定的私人求职材料目录，公开文档不保存其绝对路径。
- 私有实施记录允许保存本机路径、完整命令、阶段门禁和求职表述草稿。
- 学习卡必须包含代码导航、20 分钟实验、面试题、口述题和次日复写题。

## 6. 稳定记录 ID

每个阶段使用以下 ID：

| 类型 | 格式 | 用途 |
|---|---|---|
| Change | `E2-C01` | 一个可独立验证的行为变化 |
| Decision | `E2-D01` | 有候选方案和取舍的设计决定 |
| Incident | `E2-I01` | 实现或验证中遇到的故障 |
| Experiment | `E2-X01` | 消融、性能或质量实验 |
| Limitation | `E2-L01` | 当前不能解决或不能宣传的边界 |

阶段文档、总账、测试说明和私有学习卡使用相同 ID 交叉引用。

### 6.1 初学者术语表

阶段文档必须维护本阶段的小型术语表。下面是 E0/E1 的起始词汇：

| 术语 | 白话解释 | 在项目里的例子 |
|---|---|---|
| schema | 数据必须长什么样的规则 | `PolicyVersion` 规定版本必须有状态和生效日期 |
| invariant | 无论输入如何都不能被破坏的条件 | 每个制度族必须恰好有一个 active 版本 |
| fixture | 为测试准备的小而固定的样例 | `data/v2/fixtures/smoke` 的五份文件 |
| manifest | 一批产物的目录和身份证 | 记录每份生成文档路径、hash 和 metadata |
| hash | 文件内容计算出的指纹 | test JSON 改一个字节，SHA256 就会变化 |
| deterministic | 相同输入必然得到相同输出 | facts、profile 和 seed 相同，manifest bytes 相同 |
| ACL | 哪些用户组可以读取哪些材料的规则 | contractor 不可读取 `security_ops` 文档 |
| gold document | 评估时确认能支持正确答案的文档 | 当前有效的正式制度文档 |
| distractor | 容易被错选、但不应作为当前答案依据的材料 | 已废止的 2025 制度 |
| forbidden document | 系统里存在但当前用户无权读取的文档 | contractor 请求受限安全制度时的文档 |
| RED | 先看到测试按预期失败 | overlap 未校验时测试失败 |
| GREEN | 最小实现后测试通过 | 加入区间检查后该测试通过 |

术语表不是百科全书，只解释理解当前代码所需的含义。

## 7. 证据等级

回填历史和记录新工作时，每项结论必须标记来源：

| 标签 | 含义 |
|---|---|
| `[OBSERVED]` | 当前文件、Git、测试输出、hash 或日志可以直接证明 |
| `[REPRODUCED]` | 当前重新运行命令后得到相同现象 |
| `[INFERRED]` | 根据代码和多个证据推断，必须写明推断依据 |
| `[RETROACTIVE]` | 阶段结束后根据现存证据回填，不声称是实时记录 |
| `[NOT_CAPTURED]` | 发生过但原始输出未保存，禁止补写虚假数值或日志 |

“完成”“提升”“安全”“可复现”和“根因”必须至少有 `[OBSERVED]` 或 `[REPRODUCED]` 证据。只有 `[INFERRED]` 时应写成“最可能原因”，不能写成确定根因。

## 8. 每个 Change 的固定模板

每个 `Change` 必须按以下顺序记录：

### 8.1 元信息

- ID、阶段、状态和日期；
- 开始时 branch、HEAD 和工作树边界；
- 本次允许修改和明确不修改的范围。

### 8.1.1 先说人话

- 原来用户会看到什么问题；
- 这一步具体增加或改变什么；
- 它为什么是当前阶段的工作，而不是后续阶段；
- 最终用什么证据判断是否完成。

### 8.2 改前状态

- 用户或企业问题；
- 现有代码入口；
- 可重复的基线命令和输出；
- 为什么现有行为不足，而不只是“缺少某个流行组件”。

### 8.3 思路来源和候选方案

- 来源可以是项目失败案例、主提示词、现有代码、官方文档、研究论文或公开 Agent 项目；
- 使用互联网来源时只引用可核对的原始资料；
- 列出至少两个真实候选方案；
- 说明选择、放弃和推迟的理由，包括复杂度、延迟、依赖和可测性。

### 8.4 假设与 RED 证据

- 写出可以被证伪的假设；
- 先写或确认失败测试；
- 保存测试名称、命令、失败类型和该失败实际证明的范围；
- 如果历史 RED 输出没有保存，使用 `[NOT_CAPTURED]`，不得伪造。

### 8.5 代码修改

- 文件路径、类、函数和关键字段；
- 修改前后的数据流；
- 为什么职责放在这个模块；
- 关键分支、异常路径、预算或安全边界；
- 删除或不再使用的行为。

代码解释采用“导航 -> 接口 -> 关键分支 -> 例子”的顺序：

1. 先列推荐阅读顺序，防止初学者在文件之间来回跳。
2. 展示函数签名，逐个解释参数和返回值。
3. 只摘录真正决定行为的关键代码，并逐段解释。
4. 使用一条真实样例从输入追踪到输出。
5. 说明常见误解，例如“模型校验通过”不等于“检索质量变好”。

### 8.6 困难和调试

- 用户可见症状；
- 最初假设；
- 用什么最小实验排除或支持假设；
- 实际原因或当前最可信解释；
- 最终修复；
- 防止复发的回归测试；
- 无效尝试为什么无效。

### 8.7 结果解释

- targeted tests、full tests、评估、hash 或性能结果；
- 好结果为什么出现，证据是否支持因果结论；
- 没提升或退化时保留原结果，分析可能原因；
- synthetic、mock、rule-based 和 live model 证据必须分开描述；
- 记录仍未覆盖的风险和下一步实验。

### 8.8 学习与面试

- 一句话项目价值；
- 30 秒和 2 分钟两种面试表达；
- 可能追问及准确答案；
- 本人必须运行的实验；
- 不能宣传的内容。

### 8.9 一个 Change 的初学者示例

下面用 `E1-C05` 展示记录深度。它只是格式示例，完整证据仍写入 E1 阶段文档。

#### 先说人话

有了 72 或 600 份文档，不代表项目可以评估。系统还需要知道“应该找到哪份文档”“哪些事实必须回答”“哪些文档当前用户不能看到”。因此 E1 从同一份企业事实源生成结构化问题，而不是让另一个 LLM 临时判断答案好不好。

#### 输入与输出

```text
CompanyFacts + authoritative DocumentSpec + CorpusProfile + seed
-> build_eval_splits(...)
-> dev: list[EvalCase]
-> test: list[EvalCase]
-> serialize_eval_cases(...)
-> dev.json / test.json / test_manifest.sha256
```

- `CompanyFacts` 提供问题、答案、版本和 ACL。
- `DocumentSpec` 提供真实存在的 `doc_id`。
- `CorpusProfile` 规定 dev/test 数量。
- `seed` 只决定候选题的稳定排序。
- `EvalCase` 同时保存问题、required facts、gold、distractor、forbidden 和 UserContext。

#### 为什么不能只保存 question/answer

如果只保存问题和一段参考答案，检索失败和生成遗漏会混在一起。加入 `required_fact_ids` 后可以判断证据是否覆盖全部事实；加入 `gold_doc_ids` 后可以算 retrieval 指标；加入 `forbidden_doc_ids` 后可以测试 ACL 泄漏。

#### 关键判断

permission case 的 `expected_answer` 必须为空，因为把受限事实写进普通评估输出本身就扩大了泄漏面。no-answer case 也不回答，但原因不同：前者是“存在但无权访问”，后者是“可访问语料里没有证据”。

#### 测试怎样证明它

```text
测试先验证 dev/test 都覆盖六类任务
-> 再验证 case ID 和 question 不重复
-> 再验证 gold docs 对用户可见
-> 再验证 forbidden docs 对用户不可见
-> 最后验证 test bytes 与冻结 SHA256 一致
```

这里的测试只能证明数据 contract 自洽，不能证明真实 embedding 检索已经找得到这些文档。后一个结论必须等 E2/E3 运行检索评估。

#### 面试表达

“我没有让 LLM 自由出题再自评，而是从版本化原子事实生成 EvalCase，把 required facts、gold、distractor、forbidden 和 UserContext 放进同一个契约。这样可以把 retrieval miss、版本选择错误、权限泄漏和 generation omission 分开定位。”

## 9. 实时更新时机

从 E2 开始，每个 Change 采用增量记录：

1. 修改前：写元信息、改前状态、候选方案和假设。
2. RED 后：立即记录失败测试和输出摘要。
3. 实现后：记录文件、函数、数据流和异常路径。
4. targeted GREEN 后：记录局部证据。
5. 评估或 full pytest 后：记录最终结果与解释。
6. 阶段结束：更新总账、私有审计和学习卡，然后执行阶段门禁。

不得只在阶段结束后凭记忆一次性补齐全过程。

## 10. E0/E1 回填规则

E0/E1 已经发生，因此属于历史回填：

- 只使用当前 Git 状态、设计文件、测试、生成物、hash、终端输出摘要和已有审计记录；
- 能重新运行的验证标为 `[REPRODUCED]`；
- 能从代码直接确认的事实标为 `[OBSERVED]`；
- 当时的思考过程若没有原始记录，标为 `[RETROACTIVE]`；
- 没有保存的首次 RED 具体输出标为 `[NOT_CAPTURED]`；
- 不把后来的理解伪装成当时已经知道的结论。

E1 至少回填以下 Change：

```text
E1-C01 schema 与不变量
E1-C02 facts/profile 唯一事实源
E1-C03 deterministic 文档生成
E1-C04 五格式 renderer
E1-C05 结构化 eval 与冻结 split
E1-C06 manifest、安全写盘与 CLI
E1-C07 checked-in smoke/eval 与 Git 边界
E1-C08 data card、学习材料与阶段验收
```

故障总账至少收录：pytest helper 误收集、Windows CLI 编码、Windows staging rename、版本区间 overlap、permission split 偏斜、Codex patch 回执异常和 PowerShell JSON 编码误判。

## 11. E2 使用方式

E2 进入实现前先创建阶段文档骨架并记录真实基线。建议的 Change 边界是：

```text
E2-C01 Parser Registry 与结构化错误
E2-C02 Normalized DocumentRecord
E2-C03 多格式 fixture 与 parser contract
E2-C04 heading-aware chunking
E2-C05 parent-child 与表格 chunking
E2-C06 exact/normalized dedup 与版本治理
E2-C07 index manifest 与安全 CLI
E2-C08 staging/validation/active switch 或明确推迟理由
E2-C09 chunking retrieval 消融与阶段验收
```

实际边界必须在阅读现有 parser/index 代码后调整，不能把上述建议当作已经实现的事实。

## 12. 质量门禁

记录体系本身通过以下检查：

- 没有 `TODO`、`TBD` 或虚构命令输出；
- 每个完成的 Change 至少有一条代码证据和一条验证证据；
- 每个 Incident 有症状、诊断、修复和回归边界；
- 所有数字与当前文件或命令一致；
- 公开文档不出现私人路径和敏感信息；
- 私有学习卡仍保持“未验收，不得标记为已掌握”；
- 阶段结论明确区分“实现完成”和“能力已通过 live evaluation”；
- Git status、测试结果和未解决问题在阶段结束重新核对。

## 13. 完成定义

方案 C 的首次落地只有在以下条件同时满足时完成：

1. E0 回填实施记录存在；
2. E1 实施记录按八个 Change 重写或补充；
3. 跨阶段决策与故障总账存在；
4. 私有 E0/E1 审计和学习材料完成对应更新；
5. 所有历史内容注明证据等级；
6. 文件通过占位符、路径、数字和格式检查；
7. 用户完成书面规范复核；
8. 未经确认不 commit、不 push。
