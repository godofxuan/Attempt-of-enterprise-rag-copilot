# 面向诉求与证据的结构改进建议

日期：2026-09-12。

状态：PROPOSED_NOT_IMPLEMENTED。本文件是架构判断与分阶段建议，不是新的实验结果或完成报告。本轮只补充方案文档，没有修改业务代码、运行真实模型、修改简历或推送 GitHub。

## 2. 核心方向：全链路共享用户诉求

建议把同一请求中的诉求建立为稳定ID，贯穿查询分析、检索、补读、证据账本、答案生成和发布检查。不是再复制一份事后关键词规则。

示例原问句：“出差报消要带啥，领导签个字就行？”

候选计划应明确区分：

- N1：报销所需材料。
- N2：领导签字是否足够，是否另有审批或办理条件。
- 原始用户措辞、相关原文位置、适用范围与未知事实。

N2是待回答问题，不能被计划器改写成“领导签字就足够”。是否真的理解了这一点需要语义评测；JSON有效并不能证明理解正确。

每项诉求应分别记录，而不是用单个完成布尔值覆盖：

- `search_attempts`：做过哪些搜索；它不表示已经找到证据。
- `evidence_refs`：哪些合法、实际交付的证据与这项诉求有关。
- `read_extent`：候选位置、实际读取位置、截断与尚未读取的部分。
- `support_assessment`：支持、不支持、冲突、未知，以及判断依据和判断者。
- `missing_user_facts`：例如出差地区、时间、人员类别，不能从文档或模型中捏造。
- `answer_claims`：最终哪些陈述回答这项诉求，并绑定具体引用。

这些是建议中的字段职责，不是现有接口已经新增的字段。最终兼容设计应复用现有Pydantic模型和Evidence Ledger，避免双份状态。

### LLM的合适角色

允许现有本地模型提出结构化诉求、歧义和检索别名建议；主机保留原问句、校验类型与预算，并检查金额、日期、制度编号、否定等显式约束是否被改变。规则检查只是必要条件，不能保证所有语义都没变。

原问句必须保留，不允许一个猜测性的改写静默替换全部原始检索。歧义纠错作为备选；可能改变重要含义时进入澄清或保留歧义，而不是强制纠错。

模型输出非法、超时或不可信时回退既有路径，并记录解析不确定性。不能因为计划器漏列一项，后续全部已列项完成，就宣称原问题完整支持。

默认简单单问仍走低开销路径。是否增加一次规划调用应通过有界配对实验决定，而不是所有请求无条件多调用模型。

## 3. 文档结构与定向阅读

仅增加top-k或open字符上限不能可靠解决后部条件、跨页表格和孤立脚注。应使检索定位与答案阅读使用不同粒度，并共享原始位置与权限信息。

建议按已有解析模型渐进补齐：

- 稳定文档、版本、章节、父块与相邻块标识。
- 表格的表题、列标题、行标题、单位、脚注和可验证的跨页续表关系。
- 页码与原始位置；格式提供时保留坐标。
- 实际读取范围和预算截断标志，不能把“读取了前缀”记成“读取了全文”。

搜索先定位较小的相关块，再根据缺项读取关联章节、邻接块或表格完整语义单元。所有展开内容仍需逐项经过当前索引绑定、版本、ACL、source admission和Guard检查，不能因为父子关系就继承通行证。

跨页续表只有在结构信息足够时合并。不能仅因相邻两页都有数字就认定同一张表，也不能从摘要生成没有原文依据的缺失行。

现有include_parent与同章节find已提供部分基础。优先演进这些模块，不引入全新的检索平台。先用真实文档样本核验结构丢失比例，再决定是否更换某一类PDF解析后端。

参考：Docling的统一文档模型包含表格、层级与provenance；Haystack的AutoMergingRetriever利用层级关系把部分叶子命中提升为父级内容。这里借鉴数据模型和阅读策略，不把框架能力视为我们文档上的已验证准确率。[Docling](https://docling-project.github.io/docling/concepts/docling_document/)；[Haystack](https://docs.haystack.deepset.ai/docs/automergingretriever)。

## 4. 根据缺项原因选择动作

目标不是“多搜索几次”，而是让Controller知道下一步动作能补什么。

| 缺项情况 | 建议动作 | 不应采取的动作 |
| --- | --- | --- |
| 已找到相关章节，但必要部分未读 | 受限open/邻接/表格展开 | 无差别再搜整库 |
| 证据与其中一项诉求不相关 | 针对这一项最多一次重试或备选检索表达 | 覆盖原问句并无限改写 |
| 缺用户地区、日期、身份类别等事实 | 明确询问或给条件化说明 | 让模型猜测用户事实 |
| 合法来源之间潜在矛盾 | 保留双方有效引用并说明冲突 | 选得分最高者当作制度裁决 |
| 解析丢行、缺单位或OCR不可用 | 明示材料质量限制，进入数据修复流程 | 让模型补造表格内容 |
| 当前身份下无可用证据 | 按原契约说明无法支持，不泄露受限文档存在性 | 扩大权限或越权搜索 |

建议让模型只提出结构化的缺项及动作理由；主机仍决定工具允许范围、总调用数、超时、重复查询终止、证据增量检查和发布状态。建议与实际执行需分别记录。

LangGraph官方Agentic RAG示例展示了模型建议、结构化相关性评分和条件分支。其相关性评分不证明问题已经完整回答，也不能直接代替我们的来源准入与发布合同。[官方示例](https://docs.langchain.com/oss/python/langgraph/agentic-rag)。

沿用现有主运行链路演进，不新增平行Controller。若保留既有其他runtime适配器，应共享任务状态、工具契约和发布检查，不能各自维护一套不同含义的“完成”。

## 5. 从逐项证据组织答案

已有claims/citations和answer contract应保留，但把诉求覆盖前置到生成输入和输出，而非主要依赖生成后查词。

生成输入：每项诉求、允许使用的证据、已知缺项、适用条件和潜在冲突。

生成输出：逐项陈述、引用、条件，以及仍未回答的部分。最后统一组织为可读正文，不能因为组织语言删除例外条件或缺项说明。

发布前分层验证：

1. 主机验证来源、权限、版本、引用真实位置、格式、受限数值及状态一致性。
2. 逐项核对是否确有回答；仅主题词出现不能算支持。
3. 可选模型核对语义与遗漏，作为风险信号，不作为自证正确的唯一依据。
4. 用真人抽样检验模型与规则盲点，包括“答错但判完整”和“可答却判partial”。

对少量高频高风险制度，可评估经复核的结构化事实：主体、事项、条件、例外、数值/单位、适用范围、版本和原文引用。抽取结果只有进入复核与版本更新流程后才能作为受控事实使用。不要一次性把整个知识库自动转换为所谓真值，也不要在没有运维能力时引入事实库与文档双重失效问题。

## 6. 建议的执行顺序

| 阶段 | 有限范围 | 验收重点 | 停止条件 |
| --- | --- | --- | --- |
| P0：状态与基线 | 冻结当前候选补丁、默认入口/profile；定义共享诉求与证据契约；保留现有规则基线 | 原反例和正向控制均保留，计划解析不确定可见 | 无法绑定真实版本/证据时不做效果宣称 |
| P1：结构阅读 | 选择一种真实文档类型；复用现有parent/find/open增加定向展开与范围记录 | 后部条件、脚注和表格单位保留，权限零回归，过度partial不恶化 | 结构丢失不是主要原因时不扩建解析器 |
| P2：有界模型建议 | 现有本地模型辅助多诉求规划及一次缺项补救，不新增排序模型 | 原意、诉求覆盖、有效补读与端到端答案质量 | 与同条件非模型方案相比无足够效用收益则保留关闭 |
| P3：统一答案闭环 | 复用claims/citations，逐诉求生成及发布；确有必要再试小范围复核事实 | 少漏答且不靠全partial获得漂亮数字 | 误报完整、权限/预算回归未闭合则不得晋级 |

P0先解决契约与可测性；P1和P2的优先级还应由失败分类计数决定。不是上述所有方向都必须做完才能有交付，也不承诺四个阶段必然提升WixQA。

## 7. 配对评测与收益解释

固定源码指纹、数据/文档版本、模型与提示、检索profile和预算。先冻结开发与最终验证划分，按文档/模板分组以降低同模板泄漏。

已有WixQA两套人类200题均已消费，不能再命名为全新独立holdout。它们可作为明确标记的回归/回顾性开发集；新领域场景的外部泛化仍需新数据和人工标注。

用单项消融分离收益：当前修复版、仅共享诉求契约、增加结构阅读、增加模型规划、增加缺项补救。不同阶段的必要依赖要写清，不把换候选池的收益归因于LLM。

必须同时报告：

- 人工标注诉求的识别召回与多拆/幻造诉求比例。
- 真正正确且完整的回答比例，以及逐项证据支持与重要条件保留率。
- 错误宣称答全：全请求中的错误answered比例及answered内条件错误率，均给分母。
- 过度partial/拒答：已具备足够材料却不回答的比例，不能用全部拒答避免错误。
- 错别字、口语、否定、金额、日期、制度号的原意保持。
- 实际获得的新证据、无效重复动作、调用次数、token/资源消耗、mean及p95延迟。
- ACL、跨租户、来源准入、版本、Guard、工具预算和终止边界回归。

人工评分盲化配置与实验组；模型评分只作辅助，并量化与人工的一致性。报告配对变化、置信区间、失败类别和最差退化例，不为升级而调整最终测试标签。

本地模型不一定产生API费用，但仍占用CPU/GPU、显存与时间。把调用数和p95纳入门禁，不能把“本地免费”等同于“没有成本”。新增语义调用会增加误判、提示注入和循环风险，所以它只输出建议、不授予工具权限。

过去LLM改写和XGBoost未赢得既有排序对照，只能支持对应实验的负结论。不能由此证明结构化诉求规划必然无效；也不能忽略负结果再无限调参。必须采用不同的明确假设和冻结评测。

## 8. 不能靠结构升级消除的边界

- 文档本来没有答案、用户没提供必要事实、来源冲突没有合法裁决依据，不能靠更多推理变成确定答案。
- exact citation只证明有这段文字，不单独证明答案逻辑正确或条件完整。
- 读取一个章节不证明全库没有额外例外；完整性宣称必须限定到可核验的适用范围。
- LLM自评不是可靠证明；规则也不是通用自然语言理解器。
- 权限、租户、身份、版本等硬边界应保留。真正要改善的是边界内的任务完成率，而非放宽它们获得更多回答。

最终建议：值得进入有限设计与验证的是“共享诉求/证据契约 + 结构化阅读 + 缺项驱动控制”。不建议当前立即追加Denser、更多reranker、多个新Agent或全量重写运行框架。收益成立后再谈默认启用、GitHub发布和简历更新。
