## 2. 官方项目的对应做法

这些是文档与源码层面的模式对照，不是相同数据、硬件、模型、预算下的性能比较。不以星数证明技术正确，不宣称这些项目缺少我们没有全面审计过的能力。

### LlamaIndex：复杂问题拆分后汇总

官方SubQuestionQueryEngine示例先为相关数据源生成子问题，执行查询，再汇总中间回答。它直接说明“把复杂问题拆解”不是小众发明。

我们可以借鉴这一模式，但建议的统一诉求清单还需要保留缺项、原意、证据、适用条件及发布状态。模型生成了三个子问题，不自动证明原始问题确实只有这三项，汇总了三份回答也不证明没有遗漏。

来源：[官方示例](https://developers.llamaindex.ai/python/examples/query_engine/sub_question_query_engine/)。

### Dify和Haystack：定位与阅读采用不同粒度

Dify的父子检索用较小子块匹配，向模型提供较大父级上下文。Haystack的SentenceWindowRetriever通过source_id及split_id取命中位置前后的内容，而不是要求每个邻居也重复查询关键词。

这与我们的parent、章节定位、定向open方向直接对应。收益假设是补齐条件和背景，不是必然增加article-level Recall；展开也可能带入无关信息或挤占预算，因此仍需测量。

来源：[Dify官方说明](https://dify.ai/blog/introducing-parent-child-retrieval-for-enhanced-knowledge)、[Haystack官方源码](https://github.com/deepset-ai/haystack/blob/main/haystack/components/retrievers/sentence_window_retriever.py)。

### RAGFlow：在入库端保留版面和表格结构

DeepDoc提供OCR、版面识别、表格结构识别；PDF解析输出包含位置、表格和图片相关内容。其架构先解决文档如何被机器表示，再让检索和生成使用这些结果。

我们不应把纯文本切块加多轮LLM包装成同等级文档理解。若真实失败集中于表格或布局丢失，应该优先做该类型文档的解析对照；如果失败来自答案组织，更换解析器则可能没有收益。

来源：[DeepDoc说明与执行入口](https://github.com/infiniflow/ragflow/blob/main/deepdoc/README.md)。

### LangGraph：状态与条件分支控制检索补救

官方Agentic RAG教程用模型选择检索，并以结构化相关性评分决定生成还是改写。它提供可借鉴的状态与分支组织方式。

我们的拟议调整是把补救原因再区分为缺证据、未读位置、缺用户事实和冲突。相关性grader不是完整性证明，示例也不是我们权限、版本和发布合同的替代品。无需为借鉴分支模式再迁移一次框架。

来源：[官方Agentic RAG教程](https://docs.langchain.com/oss/python/langgraph/agentic-rag)。

## 3. 优势到底相对于谁

相对于我们当前多层分散判断的设计，统一诉求和证据状态有望降低维护与调试成本：可以明确定位是没理解、没检索到、没读到、没写入答案，还是写了但不受支持。

相对于只检索一次再生成的简单Demo，受限补读、澄清和缺项补救有望提高复杂问题的实际完成率。

相对于上述开源框架，不能声称算法领先或效果更好。我们可展示的工程价值是把这些模式接入既有身份、ACL、版本、Guard、实际阅读范围和答案发布合同，并用可复现反例核验一致性。该价值不意味着对方没有安全能力。

成本也要明确：计划器可能漏拆或幻造诉求；父级展开可能增加噪声；模型评估可能误判；额外步骤增加延迟。结构更完整并不自动等于效果更好。

## 4. 已证明和未证明的提升

| 方面 | 当前证据 | 不可扩大的结论 |
| --- | --- | --- |
| search/open冲突接线 | 固定7天/30天由host提前说明冲突并保留双方引用 | 不是通用语义矛盾检测 |
| 显式多诉求遗漏 | 固定入职材料/试用期问题不再只答材料就answered；正向完整控制保持answered | 不是模型真实完整回答率已提高 |
| 同章节续句 | 固定“还需提供行程单”可进入实际证据packet，不再依赖重复“报销” | 不是所有领域、任意长文都读全 |
| 截断与完整性 | 固定未读后部要求不再被当成完整答复 | partial增加不等于已补齐答案 |
| 工程回归 | 既有最终844项限定测试通过，包括31项新增测试 | 不是844个真人问答全部正确 |
| WixQA/FinanceBench/真实模型答案 | 本轮没有新测量 | 不得宣称本轮Recall、nDCG或准确率提升 |
| 统一诉求、通用结构阅读、模型补救 | 仍是方案 | 不得把预期价值写成已经交付的收益 |

如果原先和改进后都命中同一正确文章，article-level Recall可能保持不变；文章中的附加条件是否进入模型、是否进入回答却可能变化。三个层次要分开测，而不是为某一层选一个漂亮指标。

## 5. 主线决定

这里的“主线方向”“合并代码”和“默认启用”是三个不同决定。

| 工作 | 建议 | 合并或启用前仍需完成 |
| --- | --- | --- |
| 已完成的证据接线、有限遗漏、章节补读修复 | 进入合并准备，作为候选修复 | 核对最终差异、既有未提交修改保护、旧前提失配记录、相邻/平台CI与入口一致性 |
| 统一诉求/证据状态 | 纳入下一轮主线设计 | 先做兼容契约，不复制另一套Controller；验证原行为及新状态职责 |
| 更通用的结构化阅读 | 纳入优先实验，目标是主线能力 | 固定真实文档类型与样本；测条件覆盖、回答完整性、过度partial及预算 |
| LLM辅助规划与缺项补救 | 主线开发计划可包含；默认行为暂不启用 | 受限本地模型配对实验；原意保持、有效完成率、错误完整、p95及权限门禁 |
| 扩建新检索平台、更多ranker、多个新Agent | 不纳入本轮 | 当前没有证明这是主要瓶颈 |

已知correctness缺陷不必等到WixQA上涨才能修复或合并；但改变控制策略、扩大上下文和增加模型调用，仍需与当前修复版比较真实效用和成本。不能用“安全修复”名义跳过所有行为变更的验证。

## 6. 后续用什么结果决定默认晋级

冻结修复版作为对照，分离共享诉求、结构阅读、模型规划与补救的消融。现有用过的样本只作开发与回归；独立泛化需要未消费且预先冻结的样本。

优先指标：正确完整回答产出率、逐诉求支持率、重要条件保留率、错误answered率、过度partial/refusal率、p95、模型调用数和预算违规。模型评分只作辅助，语义结论需人工抽样。

若只是把错误answered变成partial：承认correctness价值，不称真实完整回答提升。若能增加正确完整回答且错误完整与资源成本在预设范围内，则具备默认晋级理由。若LLM没有胜过简单结构方案，保留结构改进，停止该LLM方向。

最终建议：把统一诉求与结构化补读作为后续主线方向；先收口已完成修复；模型辅助放在同一架构的可关闭策略中验证，不预先宣布成功。本轮未执行合并、发布、真实模型评测或简历修改。
