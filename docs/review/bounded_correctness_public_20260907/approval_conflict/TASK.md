## 5. 任务一：有限答案契约

### 5.1 需要修复的机制

不能用答案里存在“审批 / 批准 / approv”证明它回答了“谁审批”。

不能用被引用来源的 `aspects` 证明最终 claim 覆盖了所有所问方面。

不能用 `len(required_aspects) == 1` 把一个实际含两个问题的响应整体清空。

### 5.2 识别范围

只做有限、可测试的审批角色与时长问题处理，不实现通用语义理解。

至少支持：
- 谁审批、由谁审批、需要谁审批、谁批准、哪个部门审批、哪位审批；
- 审批人是谁、审批由谁负责；
- 现有有限英文 `who ... approv` 问法；
- 现有时长问法，以及明确的“提前多少天/几天提交 + 审批人”二元问法。

判断审批角色必须绑定审批谓词，不得把提交人、核验人当审批人。

使用有限句式和关系位置处理，不硬编码 case ID、文档 ID、某一个部门名称或固定正确答案。对无法可靠理解的结构保守处理，不不断追加同义词和前缀。

保留现有 `answer_sufficiency()` 对已冻结调用的兼容语义。例如“只问审批人、只有提交天数”仍应产生 `missing_requested_relation`。可在同文件内部增加结构化判断辅助函数，不需要新服务或外部依赖。

### 5.3 本任务固定的状态契约

以下规则中的“有支持”指最终保留的 claim 已通过现有引用核验，而且在本轮有限规则内对应当前问题的对象、条件和关系。引用通过仍不是通用语义正确性证明。

A. 明确给出适用审批主体：可以 `answered`，但前提是无其他未解决方面、冲突或已有降级原因。

B. 明确说明当前对象、当前条件下完全无需审批：可以 `answered`，保留免审批条件，不编造审批人。

C. 明确说材料未说明审批人：必须 `partial`，保留引用，正文说明无法确定审批人。未知不等于免审批。

D. 只说需要审批或按流程审批：必须 `partial`，保留这项相关事实及引用，正文说明未确定审批主体。

E. 只问审批人，证据仅有提交天数等不回答该关系的事实：`not_found`，按原 source-free 契约返回，不把天数当审批答案。

F. 同问天数与审批人，仅有一项有效支持：`partial`，保留该项和引用，正文明确另一项缺失。

G. 两项都有适用支持且无其他阻断：`answered`。

H. 当前条件不能确定，例如金额未知且制度按金额分支：`partial`，可以展示完整、有引用的条件规定，但说明无法确定当前适用分支，不替用户假定金额。

`answered` 只表示本轮有限所问槽位得到支持，不代表通用业务正确、人类确认或法律裁决。

### 5.4 对象、条件、否定和单位

只在已经准入、已经交付、已有引用支持的内容上检查。不能读取模型未见的尾部、旧版本或无权限材料来补答案。

不能把“另一类申请无需审批”套到当前对象。

不能把“无需经理审批”当成“无需任何审批”。存在“仍需部门负责人审批”时，应识别后者，而不是把整个回答标成免审批。

不能把“未说明是否无需审批”当免审批。

问金额超过 100 元时：可以保留完整两分支规定，也可以给出有证据支持的高额分支；不能只给低额审批人并标成完整。

不要从完整证据中去掉关键条件后发布无条件规则。现有 citation verifier 不改弱；有限答案判断也不能对错对象、错条件、错单位的 claim 计为槽位已满足。

若条件无法在本轮有限范围内可靠对应，降级并说明未确定，不实现通用条件解析器。

### 5.5 发布一致性

正文必须同时呈现已支持部分和缺项说明。不能只在 warnings 中提示缺审批人，而正文看起来是完整答案。

示意：
“出差申请须提前 7 天提交。[沿用现有有效引用表示] 现有可用材料不足以确定该申请的审批人。”

其中证据事实保留原 claim/citation；host 的“无法确定”说明是系统对证据充分性的判断，不伪装成原文引用，也不新增虚构证据 claim。

严格区分“生成内容没有回答”和“原材料没有说明”。默认缺项说明采用“当前已核验的回答尚未确定……”之类有限表述；只有证据明确支持未知事实时，才说“该材料未说明审批人”。不得因为模型漏掉角色，就断言原文或整个知识库没有角色信息。

对应模式：
- 正常完整回答：`answered`，沿用现有正常完成 stop reason；
- 已知部分、未知关系或潜在冲突：`partial` / `partial_evidence`；
- 无可用所问事实：`not_found` / `not_found`，遵守原 source-free 契约。

其他 `permission`、`unsafe`、`security_filtered`、`budget`、`system` 等模式保持原含义，不能被答案槽位检查升级成 answered。

发现不支持的额外 claim、既有冲突或其他降级原因时，不能仅因某个槽位识别成功就抹掉原降级。

检查本次相关的生成成功、引用过滤、extractive fallback 和 source-free 路径；不能只在一种正常返回路径加检查，让 fallback 绕过相同有限契约。

### 5.6 覆盖计数

保留：
`retrieval_coverage_basis = query_anchor_relevance_not_semantic_proof`

检索方面覆盖、打包来源覆盖和最终答案覆盖是不同概念，不能互相替代。

对本轮有限问法记录请求槽位数、满足数、缺失数，满足数 + 缺失数 = 请求数。可沿用现有 `answered_aspect_count`、`missing_answer_aspect_count`，补充明确的请求数和 bounded basis。

二元问题只有天数时，应为请求 2、满足 1、缺失 1，而不是因为一个 `process_steps` 来源被引用就记录全覆盖。

超出本轮有限范围的问法，保留 `semantic_completeness_unverified` 等真实边界，不能套用虚假的语义全覆盖计数。

公开 trace 只增加必要的有界计数和固定分类标记；不放原文、问题内容、身份、路径、私有来源元数据，不放宽现有 trace 的安全限制。

### 5.7 固定验收矩阵 A

每行建立稳定 case ID，并覆盖实际生产辅助函数与适用的 HTTP 发布结果。核心状态用例必须走真实应用、认证、准入、引用及响应链；模型部分可以是明确记录的桩。

| ID | 问题与证据/生成条件 | 必须满足 |
|---|---|---|

## 6. 任务二：跨 policy 的窄范围数值潜在冲突

### 6.1 必须区分的概念

同 policy 只能有一个 active authoritative，是版本治理约束。

两个不同 policy 各有一个合法 active authoritative，可以同时存在。

来源准入只决定内容是否允许参与；不等于这些内容语义一致。

单文档 host 摘录不等于跨制度语义裁决。

本轮只识别有限的“潜在数值冲突”，不判定哪一本制度拥有最终优先级。

### 6.2 最小实现要求

先读 `_numeric_conflicts()` 的现有分组键和调用链。新增跨 policy 的有限可比检查，不能只删除 policy_id 后把所有数值混比。

可比范围仅限：
- 已由真实生产准入链允许、对当前身份可见的证据；
- 当前请求已有的合法索引快照和有效状态；
- 相容且明确的租户、地域、适用对象、作用域/条件；
- 相同事实谓词、相同完整条件模板、相同单位；
- 现有简单数值模板可以可靠提取的数值差异。

跨 policy 不要求 policy_id 相同，也不要求它们的 version/version_id 文本相同。版本号不是可直接跨制度比较的业务优先级。

保留现有权限、快照和作用域边界，尽量复用现有标准库逻辑。模板归一化不能删除否定、条件、对象、时间限定或单位。

不能把 7 个自然日和 7 个工作日、元和美元、不同比较条件或不同有效时期粗暴合并。输入没有足够元数据或明确语义时不猜测，也不新增元数据平台。

未检测到本轮可比数值冲突，不等于已经证明两制度一致；报告必须保留检测范围。

### 6.3 冲突响应

对固定夹具中可比较的 7/30 天：
- 两份合法来源保留原身份；
- host 返回 `partial` / `partial_evidence`；
- 正文展示双方数值与各自可支持引用；
- 正文明确“现有可见材料存在潜在不一致，无法据此确定唯一期限”；
- warnings 同样提示，不能只把提示藏在 warnings；
- 不发布任何“优先按 7 天/30 天执行”的胜者判断；
- 使用已有 host 摘录路径，生成模型不调用，`generation_attempts` 与 spy 一致；
- 不增加检索、候选、上下文或输出预算。

既有 `build_conflict_response()` 在 `runner_v2.py`。需要正文提示时只局部修改该函数或其现有调用处，不扩改 runner。

摘录受到现有长度/数量限制时，不用未交付文本补写数值。如果无法完整展示支持，仍保守 partial 并说明限制，不能假造双引用。

禁止删除一份候选、修改 policy_id、把文档降为 supporting、改权威分、择第一条或随机择一来掩盖冲突。

## 11. 交付格式

只建立一份新的正式审核输出目录，并将它打包为：
`RAG_BOUNDED_CORRECTNESS_<实际RUN_ID>.zip`

无需复制全部历史审核包或新增审计框架。交付应至少包含：

### 11.1 `REPORT.md`

写清：
- 实际修改的是原 worktree 还是隔离快照；

- 有限演示步骤、最多 3 条简历表述、不能宣传的能力；
- 最终结论与停止原因。

### 11.2 `TARGET_IDENTITY_AFTER.json`

包含输入包摘要、本轮开始与最终源码指纹、文件范围/算法、生产差异文件列表、真实 Git 身份或明确的无 Git 状态、实际工作区与解释器来源。

不要用审核输入的 c939... 指纹冒充修改后身份。新增测试必须纳入适用指纹范围。

公开交付中的本机路径可脱敏，但本地应保留可定位信息与映射；不能因此伪造来源。

### 11.3 `TEST_RESULTS.json`

每次命令记录：
- 唯一 run ID、阶段、组别；
- 实际命令、cwd、解释器、平台、必要插件；
- 开始/结束时间、实际退出码；
- 收集/通过/失败/跳过/错误数及 node ID；
- 测试前后源码指纹、测试文件摘要、是否发生运行中源码变化；
- 日志、JUnit、observations、imports 记录的相对路径及真实摘要；
- fixture/模型桩性质、实际 stub 调用和真实模型调用情况；
- 矩阵 A/B 每项到实际测试与结果的映射；
- 失败分类及不能验证的原因。

结果和失败分类分开：
`result = PASSED / FAILED / BLOCKED / NOT_RUN`

分类可使用：
`PRODUCT_ASSERTION_FAILURE / ENVIRONMENT_FAILURE / FIXTURE_FAILURE / LEGACY_PRECONDITION_MISMATCH / NOT_VERIFIED`

退出码非 0 不能写 PASSED。没有执行的数据用 null 或明确状态，不能默认填 0。旧测试前提失配仍保存 FAILED。

### 11.4 本轮差异和文件

提供相对于本轮开始快照的 `changes/this_round.patch`，以及所有新增/修改源码和测试的完整文件，使用相对 WORKTREE 路径。

原有未提交修改与本轮修改分开；不能把全部 HEAD 后差异称为本轮新增。

### 11.5 日志、观察记录和清单

保存必要 `logs/`、`junit/`、`observations/` 和 `ARTIFACT_MANIFEST.json`。

清单覆盖实际正式交付文件的字节数和 SHA-256，排除自身，避免自引用摘要；明确排除私有 scratch、缓存、虚拟环境、权重、原始私钥/JWT 和无关数据。

只有同时满足以下条件，才能写“有限修复完成”：

- 任务一、二的固定矩阵通过实际执行验收；
