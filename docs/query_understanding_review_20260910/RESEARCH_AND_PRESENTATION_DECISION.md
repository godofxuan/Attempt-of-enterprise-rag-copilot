## 先纠正我们的定位

当前 `retrieval_query` 是报销场景六条手写别名的兼容补丁，不是通用中文纠错，不是自然语言理解系统。
原开发集刻意包含已知别名，不能据其结果宣称陌生错字、真实企业口语或隐含诉求已经解决。
方法简单不等于无价值，但价值应体现在可维护性和用户效果上；六条别名不值得单独占一条简历。
即便否定、金额和日期字符未改动，也不等于已经证明整句语义保持。

## 官方产品和开源实现如何处理

下面列的是官方文档可确认的机制，不是对所有企业内部实践的概括，也不是本地实测结果。

### 1. 企业术语与同义词管理

Elasticsearch 支持用 API、界面或规则文件管理同义词集合，配置搜索分析器，并测试分析结果。适合简称、术语别名和稳定领域表达，不代表能够理解所有错别字。
学习重点是把词表视为有来源、可维护、可测试的配置，而不是在代码里不断增加字符串替换。
本项目尚无从授权语料/实际失败查询中形成的成熟术语维护流程。

来源：[Elastic 同义词配置](https://www.elastic.co/docs/solutions/search/full-text/search-with-synonyms)。

### 2. 从语料生成纠错候选

Elasticsearch fuzzy query 使用编辑距离匹配近似词；term suggester 从指定索引字段生成词候选，phrase suggester 加入词共现和 n-gram 统计选择短语。它们不要求人为列出每一种错误写法，但依赖分析器和索引语料；候选膨胀也有性能成本。
中文需要验证分词、同音字和专名歧义，不能把英语示例直接当作中文效果证明。

来源：[Fuzzy query](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-fuzzy-query)、[Term/Phrase suggesters](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-suggesters)。

### 3. 专门的中文纠错模型

开源 pycorrector 提供 KenLM、MacBERT、T5 等纠错实现，不只依赖人工映射。它表明中文纠错可以使用上下文模型，但项目模型报告不证明对本企业制度、人名、编号或否定条件有效。
本轮未下载、运行或选用这些模型；是否引入必须先证明现有模型和检索无法解决足够多的真实失败。

来源：[pycorrector 作者仓库](https://github.com/shibing624/pycorrector)。

### 4. LLM 查询扩展与检索反馈

Haystack 的 QueryExpander 使用聊天模型生成语义相近的多种问法，提供扩展数量及是否保留原查询的参数，并与多查询检索组件组合。
Azure AI Search 的查询改写用生成模型形成替代查询，同时检索原查询；官方明确提醒改写可能丢失精确标识符。查询改写当前文档标为 Preview，不能当作不受限制的生产推荐。
LangGraph 的 Agentic RAG 教程演示先判文档相关性，不相关时改写再检索。这是可参考的控制流程，不是“相关即充分”的证明，也不证明本地模型必然受益。

来源：[Haystack QueryExpander](https://docs.haystack.deepset.ai/docs/queryexpander)、[Azure 查询改写](https://learn.microsoft.com/en-us/azure/search/semantic-how-to-query-rewrite)、[LangGraph Agentic RAG](https://docs.langchain.com/oss/python/langgraph/agentic-rag)。

## 我们不是从未试过 LLM 扩展

仓库 `docs/retrieval_strategy_bakeoff_v1/RESULTS.md` 保留了旧 S4 实验：本地 qwen3:8b 提两条替代查询，主机检查实体/数字等约束，200 题中 110 接受、90 回退。
在那一版已消费 WixQA 协议中，三轮均值 Recall@5 为 59.25%→62.83%，nDCG@5 为 47.16%→48.44%，MRR 下降 0.10 个百分点，p95 为 197.18ms→1147.98ms。
它不是当前 raw50 74.25% 配置的对照，不是中文错字实验，不是新 holdout，不能将这些历史数拿来宣称本轮已解决纠错问题。
因此不能因为官方有 QueryExpander 就立即全量开启，也不能因为此前某版代价高就断言 LLM 永远不值得用。

## 合适的最小下一步：建议，尚未实施

1. 不继续手工堆别名；先定位用户查询失败究竟是拼写、术语、隐含诉求、检索、证据打包，还是答案发布误拒。
2. 若启动改写试验，复用现有模型和实验组件，保留原查询，最多一次结构化改写调用；不新增模型和框架。
3. 将意图澄清与检索改写分开。未知个人报销条件应向用户确认，不能由模型编造；改写产生的是检索候选，不是事实答案或权限指令。
4. 数字、单位、日期、否定、专名和制度编号做显式差异检查，仍承认检查不等于全语义证明；不确定就保持原查询。检索必须继承原始身份、ACL、时间和版本约束。
5. 原查询与扩展查询分别检索，在相同文档作用域内合并候选，再用现有 BGE 重排。额外检索/embedding/reranker工作量要计费计时，不能因为没新增模型就说没有成本。
6. 同题比较当前 helper、关闭 helper、受限模型扩展三种策略。测试正确输入的误改、未写进别名表的错字、真实口语、专名/金额/否定以及多诉求；不为测试题逐条补规则。开发与确认集按意图/模板分离，已看过的数据只算开发/回归。
7. 同时报告检索 Recall/nDCG、最终有据诉求覆盖、错误 answered、不必要 partial、模型调用与 p95。冻结预算/验收阈值后才打开确认标签，不用改阈值或只挑好题让方案通过。

当前优先级判断：表格未找到证据和多项要求过度 partial 是已有明确缺口，比扩大六条别名更值得处理。原协议 multi_table 组 19/36→9/36 的退化需要保留；不是靠查询改写就能自动修好的同一问题。

## 展示决定

不再把有限别名表作为简历或 README 成果亮点。只有在明确范围的未消费确认数据上获得可复核收益，才能新增“查询鲁棒性”类效果声明。届时也应写用户效果、原意保持与成本，而不是“接入某某框架”或“维护多少条替换规则”。
