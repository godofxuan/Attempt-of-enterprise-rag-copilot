# Enterprise RAG / Service Agent：长期产品与总体架构

> 本文是目标设计，不是已实现能力清单。现状依据来自10/13封存源码与本次可读的历史设计；执行时以当前工作区为准。公开参考对应`REFERENCES.md`的R编号。

## 1. 先把产品定义清楚

产品不再是“一个RAG接口＋一个借用Demo＋多个实验运行器”，而是**本地优先的企业知识与服务工作台**。知识问答是一项独立功能，服务办理是另一项；它们共享知识、模型与运行基础，但不混淆结果。

用户得到三种不同交付：

| 用户意图 | 产品交付 | 什么不算完成 |
|---|---|---|
| 理解制度或资料 | 有依据的答案、适用条件、可打开的来源 | 只给一个相关文档名，或引用合法但没回答问题 |
| 比较和准备业务 | 可编辑需求、可用选择、具体预览 | 只有模型说“可以借”，没有日期/设备/规则支撑 |
| 正式办理并跟踪 | 数据库中的申请、编号、实际状态及后续入口 | Agent说“已完成”，但没有申请或把待审批说成已分配 |

主用户是需要查制度和办理IT服务的员工；次用户是维护资料、配置现有模型和演示项目的开发者/管理员。先完成这两个角色的真实使用路径，不先建设企业组织架构、市场插件和万能个人助理。

### 1.1 五个贯穿全项目的设计原则

**产品对象比聊天记录重要。** 问答有会话与来源，办理有任务、参数、预览和工单，刷新页面后都能找到；不能只存在一段模型文字里。

**确定的事情交给代码，不确定的事情交给模型。** UI表单、版本冲突、数据库提交、既有业务规则由普通程序处理；模型负责理解自然表达、选择相关工具、解释资料、组织可行选项。

**复用能力，不复用别人的全部部署复杂度。** 用成熟框架已有的生命周期、类型、工具协议和事件机制，不自造通用Agent框架，也不把六个开源平台都安装进项目。

**围绕一个完整场景做纵向切片。** 从用户点击到数据库和页面结果跑通，再抽取共同部分。不能用几十个空目录、接口壳和静态效果图当进度。

**新意来自用户能够做什么。** 优先实现“从知识到任务”“改动只重算受影响部分”“可比较的真实备选方案”，不靠多Agent数量和新名词制造卖点。

## 2. 学习优秀项目的总体思维

### 2.1 Open WebUI：先有可进入、可配置、可回来的工作空间

其Workspace把模型、资料和其他能力组织成用户可操作对象，而不只暴露一次模型请求。[R01] 我们学习的是：用户先进入工作台，再连接模型、整理资料、继续历史；设置与资源状态本身也是产品功能。

我们的落地不是复刻Open WebUI，而是四个主页面：知识问答、服务任务、资料库、设置。一个应用入口，固定持久目录，模型未就绪时仍可查看数据和配置。

### 2.2 Deep Agents / LangGraph：区分运行时、Agent循环、具体业务

Deep Agents的架构说明区分LangGraph运行时、LangChain Agent抽象和上层harness装配。[R02] 这帮助我们避免把业务规则、模型重试、任务持久化和UI渲染都塞进一个图节点。

本项目保留LangGraph作为执行基础，形成一个薄的服务Agent装配入口；领域服务才负责库存、资格、预览和申请。上下文构造、错误归一和工具描述分别有清楚职责。暂不安装完整Deep Agents，更不叠一层“自研harness框架”。

### 2.3 Onyx / RAGFlow：知识系统从文档生命周期开始，不止Top-k

Onyx搜索工具明确区分搜索、结果组织、连续上下文，以及返回模型与UI的不同表示；RAGFlow提供检索测试来定位解析、召回和回答阶段的问题。[R03–R04]

我们的落地是完整资料链：文档 → 版本 → 解析/切块 → 索引代次 → 检索证据 → 答案 → 可点击来源。相同证据对象供RAG和Service使用。问题在解析就修解析，不因为答案不好就增加另一个judge。

### 2.4 Dify：执行过程是用户可见的运行，不是一次HTTP黑盒

Dify的运行器将底层工作流事件转换为应用层事件。[R05] 我们保留这个分工：应用服务推进工作，事件告诉用户发生了什么，页面从快照和增量事件恢复。无需复制工作流画布、插件daemon或它的整个调度系统。

### 2.5 Paperclip：围绕可继续的任务组织长期工作

Paperclip将issue作为工作对象，关联状态、文档、讨论和执行。[R06] 我们借鉴“任务可回到、信息可更新、下一步明确”，而不是组织级多Agent管理。

电脑借用不是一次对话结束即消失。用户可能隔一段时间改日期、补用途、查看审批状态。任务视图必须能表达这些正常变化。

### 2.6 Superpowers与Codex Goals：开发过程对着结果推进

调试时借鉴Superpowers的根因调查，而不是复制其所有审批或测试仪式。[R15] 持续实施采用原生Goal加持久计划：遇到错误自行诊断，目标不变，方案可以局部调整。[R12–R14]

这里的自主开发者是Codex；产品里的业务Agent不会自动修改代码、部署环境或变更业务规则。这是两个不同层面的自主性。

## 3. 目标系统：模块化单体，边界清楚

```text
用户工作台：知识问答 | 服务任务 | 资料库 | 设置与历史
                             |
                     FastAPI + 静态前端
                             |
          应用服务：知识问答 / 文档作业 / 任务操作
               /                              \
      KnowledgeService                   ServiceTaskService
      统一检索、证据、回答                 参数、预览、工单
               ^                              |
               +----- 知识工具 ------- Guided Agent
                                              |
                               Service Catalog + 领域工具
                             |
   共用基础：模型适配器 / 本地作业 / 运行事件 / SQLite / 文件索引
```

默认一个Uvicorn应用进程，Ollama继续是已存在的外部模型服务。解析和索引计算放到有界工作执行器，模型网络请求采用异步接口，不能在ASGI事件循环里阻塞所有页面请求。

现有`ServiceContainer`、`create_app`、索引发布和SQLite事务能够承担这些职责时直接改进；不建立第二个名字不同、功能相同的容器。配置在组装入口确定，API和工具只拿依赖，不到处读取环境变量。

双产品入口不需要双份完整源码。历史双worker可以留在实验路径，但不再是README默认启动链。以后真的需要独立部署知识服务，再沿已清晰的接口切开，而不是现在提前保留两套平行实现。

### 3.1 哪些能力现在保持不动

保留FastAPI、Pydantic、SQLite、Ollama、BGE-M3的当前有效dense embedding路径、FAISS、BM25/RRF和LangGraph；保留有效解析器、索引代次切换、已有申请唯一性、确认与读回。

不因为BGE-M3支持其他模式，就宣称代码已经使用其稀疏或多向量能力；不把FAISS精确检索包装成百万规模ANN方案。当前优先让已实现能力在产品中真实可用。

### 3.2 哪些必须退出默认链

运行时切换两棵`app`、通过`sys.path`与monkeypatch选择配置、产品导入测试fixture、每次启动新runtime、整个源码指纹扫描、历史模型授权账本链、多代writer/route的默认混用、对同一知识正文的完整重复审查。

它们分别进入一次性迁移、实验入口、历史版本或被共同实现替代。不是逐个强制删除文件；重点是正常用户不再被这些旧机制阻塞。

文档去重、锁文件和数据兼容校验可以保留必要实现。我们取消的是过量的证明与重复核验，不是盲目删除所有包含`hash`或`validate`的代码。

## 4. 应用底座：一条命令真正启动

### 4.1 安装、初始化、日常运行分离

目标命令（待实现，不代表现在已经可用）：

```bash
uv sync --locked
uv run --no-sync esa init --sample
uv run --no-sync esa serve
```

安装负责依赖。`init`创建缺少的配置和目录，可选加入明确的合成资料/业务样例，重复执行不覆盖现有数据。`serve`只启动应用，不自动下载模型、重建全库或生成新数据库。`doctor`作为出问题时的显式诊断，不是每次用户点击的门禁。[R09–R10]

模型或嵌入未就绪时，样例文档保持“待处理”，不能假装已经建立可检索知识库。离线测试可以使用fixture，但前端和结果标明测试模式，不能静默冒充实际Ollama。

### 4.2 依赖与配置

补齐真实项目元数据、console入口和锁文件；直接导入的依赖直接声明，开发工具与可选实验依赖分组。Python版本根据真实主环境与原生库兼容性确定，不能把“理论上支持Windows/Linux”写成均已验证。

配置分为：启动配置（数据根、监听地址、端口）、模型配置（已有endpoint/tag、超时/并发）、知识配置（默认库和检索profile）、业务配置（服务目录与示例规则）。固定优先顺序为显式启动参数 > 环境变量 > 配置文件 > 默认值；UI保存的用户设置属于配置文件/设置仓储，不再形成多个互相覆盖的来源。

先读取现有入口和环境，解决一个真实启动错误再继续。依赖问题定位到具体包和ABI，不随机升级整套LangChain，也不靠安装完整测试环境掩盖产品导入tests的问题。

### 4.3 数据与资源生命周期

```text
data/
  app.sqlite3
  documents/
  indexes/
  logs/
```

这是目标布局，不是要求把已有活动库复制一份后丢掉旧记录。真实目录固定、显示绝对路径；迁移先保留原库，切换后只有一个活动位置。备份采用SQLite一致性备份或停写流程，不能在写入中的WAL数据库上只复制主文件就声称完整备份。

应用工厂不隐式加载全部模型/索引。Web先可用，索引和模型能力状态分别显示；昂贵资源在实际需要时初始化，并记录原因明确的失败状态。初始化后失败的依赖可通过设置页面重试，不要求重启整台机器。

模型服务统一管理连接、超时、流式、排队和已有模型驻留配置。默认低并发起步，记录排队与生成耗时；不要同时让嵌入批处理和多份review模型占满显存。资源安排依据当前机器，不承诺固定提速比例。[R08、R11]

### 4.4 功能就绪而不是全局红灯

- Web与存储正常：历史任务、资料列表和设置可用。
- 聊天模型缺失：生成类操作不可用，显示模型名和处理入口。
- 嵌入不可用：新向量建库暂停；已经可用的功能根据实际依赖决定，不能全部消失。
- 单个知识库索引坏了：该库显示问题，不阻塞其他库和业务回执查询。

设置页可诊断、可重试，不自动扫描或下载新的大模型，不以“fallback成功”掩盖配置错误。

## 5. 知识产品：资料到答案的完整生命周期

### 5.1 文档管理

知识库支持创建、改名、说明、默认选择；文档支持上传、解析状态、原文/解析文本预览、替换版本、停用/删除、重试失败处理。第一版使用已有解析器支持的PDF、DOCX、Markdown和TXT；扫描PDF未配置OCR时明确提示，不自动把空文本标为成功。

保留文档ID与版本ID的区别：一个文件更新不需要换成完全无关的文档。历史答案保留当时引用的版本；新问题检索当前启用版本。需要删除内容时同步取消新检索可见性，不只从磁盘删除原文件。

### 5.2 导入作业

一次上传对应可查询的作业记录。阶段至少能表示接收、解析、切块、向量化、索引发布和完成/失败，页面显示实际正在处理的阶段与计数，不造百分比。

先复用`app/indexing/store.py`、增量计算及可恢复嵌入的有效能力。对仅为历史实验校验存在的包装逐步收敛，不再另写一整套索引发布器。作业中断后继续可重入阶段；不能把内存BackgroundTasks当作可靠持久任务队列。

新索引完整生成后切换活动代次；单次查询使用同一代。索引元数据记录嵌入模型、维度、归一化和切块配置等真正影响兼容性的内容。

R2增加用户明确选择的目录导入。默认预览新增/修改/缺失，手动同步即可，不先做全天候watcher。来源文件缺失默认停用相应来源，是否永久删除需采用界面明确设置；不能顺手遍历磁盘中的私人文件。

### 5.3 检索与上下文

保留混合检索和RRF。修好去重、相邻片段合并、标题/表头/必要条件带入，再判断是否需要reranker。版本与知识库范围在检索入口和材料化时一致，不把不该参与的文档混到生成上下文里。

分数用于排序，不显示成“答案正确率97%”。向用户展示可理解的来源与不足；开发者可以查看关键词命中、向量候选与融合结果，以定位问题属于解析、召回、排名还是生成。

### 5.4 两种问答模式，而不是两套知识系统

**快速问答**：必要的上下文整理 → 混合检索 → 证据组织 → 一次主要生成 → 现有结果契约发布。简单问题不预先创建计划、多个reviewer和后台调查。

**深入查找**：用户明确选择或问题确实需要跨文档查证时，允许同一Agent有界调用`search`、`read`、`find`，必要时分解子问题，最终在同一结果契约中给出结论、差异和不足。不是另起一个框架，也不默认让每个问题走复杂链。

普通模式的一次主要生成不是承诺整个请求永远只有一次模型调用：需要追问消歧、查询改写时应显示真实调用，不为满足数字删掉必要处理。优化目标是去掉无用的重复模型判断。

### 5.5 一份正式知识结果，两个入口消费

`KnowledgeService`复用现有`AnswerResponse`和`EvidencePacket`。问答页面直接呈现；Service需要完整知识答案时附加该结果对象，不先变成字符串再让另一个writer重写。

Service只需要业务规则时，应读结构化规则与对应来源，不额外生成一整篇知识答案。借用时如果用户另问政策，页面可同时显示“政策解答”和“当前办理状态”，不需要把二者混成新的一份巨大结论。

对金额、否定、例外和适用主体保留原有有效行为；A1用作针对性回归，不扩大成每个请求都要做的一套独立审计。

### 5.6 冲突、过期和没有答案

多个有效资料冲突时展示出处及时间/适用范围，不能默默选一个并标成统一政策。来源更换后，历史回答仍注明引用版本；用户点“按最新资料再回答”才生成新结果。

找不到依据时给出已查范围、缺少内容和可行下一步，例如选择另一知识库、补充文档、转人工确认。不能用一个“低置信度百分比”代替实质说明。

## 6. Service：一个可持续编辑和继续的业务任务

### 6.1 创建与表达

保留引导式范围选择。入口可以是服务卡片、结构化表单或自然语言，但最终形成一个明确任务简报：服务类型、用户要达到的结果、当前参数、仍缺的信息、允许做到哪一步。

自然语言只做必要的参数提取与局部变更识别。模型提议的日期等字段在界面可见；确有歧义时问一个针对性问题，不反复要求用户确认同一意图。相对日期按项目业务时区与请求时点解析并显示绝对日期，不按隐含设备时区猜测。

### 6.2 用户修改

复用`facts_revision`并补齐原子比较；旧页面收到冲突后展示新值与当前编辑，不能静默覆盖。未传字段与显式清空区分，允许缺失的字段清空后回到待补状态。

保存之后自动触发受影响的业务处理。没有变化则保持现有预览，不重新调用全部工具；有变化则旧预览失效，允许新预览。取消“整个任务只能预览三次”这种用历史总数限制正常编辑的机制，预算约束放在单次执行和无进展循环上。

### 6.3 业务服务与工具

Agent可用工具围绕真实业务：当前规则、资格、可用设备、已有申请、相关知识、准备预览、读取回执。业务逻辑只在领域服务一处；工具是类型化薄适配。

用户身份、task_id和当前版本从宿主上下文注入。模型不必重复拼这些字段，更不能通过改工具参数选到别人的身份。

工具返回区分“有效但没有可用设备”“参数缺失”“暂时连接失败”和“成功产生预览”，而不是全部变成一段错误字符串让模型猜。

### 6.4 正式提交退出模型循环

界面展示确定的设备、日期、用途和实际业务影响。用户确认这个具体预览后，API直接执行既有confirm → submit → readback；模型不再决定是否调用正式提交，也不判断数据库是否真的成功。

保留一处事务、幂等键与实际读回。两个重复点击只产生一个申请。待审批就是待审批，不写成设备已经分配。

这里的必要确认是正常交易交互，不是扩张安全框架。用户选任务范围一次、最终提交确认一次；查政策、库存、读回不层层弹确认。

### 6.5 任务的完整寿命

已提交任务默认只读与跟踪。用户再说“改日期”，要区分修改草稿和修改已提交业务单：后者只有业务适配器真的支持时才开放；否则明确说明可做的动作，不静默改历史申请。

R1保留当前借用操作与查询，不凭空引入撤销审批、提前归还或自动续借。R2的新服务也只声明实际实现的动作。

## 7. Agent运行层：薄循环与紧凑上下文

### 7.1 不需要六个角色协作完成一次借用

沿用LangGraph，将逻辑收敛为读取当前状态、构造上下文、模型选择、工具执行、记录观察、判断暂停或继续。最终业务事实由领域服务提供。工作流与动态Agent各有职责，不为了“像Agent”把确定性规则移进提示词。[R07]

标准工具调用优先复用成熟接口；当前模型不兼容时只保留一个显式转换适配器。先检查实际安装版本，不为了跟上README最新代码升级所有依赖。[R08]

### 7.2 ContextBuilder管理信息，不管理一套平行事实

给模型的上下文按优先级组织：当前用户目标与范围、最新参数、当前业务状态、已知有效观察、相关证据片段、最近一小段动作与用户消息。长文档用片段和可继续读取的引用，不全文复制。

结构化参数不靠对话摘要恢复。重复工具输出去重，过期结果明确标记；长历史只作为背景摘要，不覆盖当前日期、设备和申请状态。摘要是派生数据，可重建，不成为业务事实来源。

默认不用额外LLM每步压缩上下文。先确定性裁剪、保留必要信息；确需摘要时在长会话阈值触发，不每轮再开一个“记忆Agent”。

### 7.3 失败处理分工

传输瞬时错误可以少量重试；缺字段转为补充问题；无库存给真实备选；模型输出结构错误做一次有上下文的格式修复或明确失败。重复相同工具且无新观察时停止空转，解释阻塞与下一步。

单次run有步骤和时间上限，可配置。用户给了新信息是新的业务推进，不受任务过去累计工具次数永久封锁。不要通过无限重试制造“自主”。

### 7.4 恢复选择

默认恢复业务状态，不承诺从某个模型token原地续写。任务、参数、预览、申请、必要观察在SQLite中；进程重启后创建新的短run，读取当前事实继续。旧run结果不能覆盖更新后的revision。

本轮不同时引入另一份完整LangGraph持久状态作为业务真相。若未来确需复杂调查长图恢复，可以使用官方checkpointer保存图内执行状态，但申请/库存仍由业务数据库负责。[R07]

## 8. 三个重点差异化功能

这些是面向本项目的工程与体验设计，不宣称新的学术算法。

### 8.1 从知识答案直接进入任务

用户先问“维修期间能不能借一台电脑”，得到有来源回答。界面显示一个有依据的“开始借用”入口，打开预填的任务草稿，沿用来源、已给出的信息和当前会话关联，不让用户再复制粘贴一遍。

动作建议来自服务目录和结果中的结构化需求，不是任意把模型文字当可执行指令。点击后用户仍看见任务范围与参数；答案仅作为背景，不自动授予提交权限。

实现复用现有答案/任务对象，以关联ID连接，不发明一套“知识到动作证明协议”。

### 8.2 改动影响分析：只重算受影响的东西

在领域中维护一张小型依赖表，而不是构建通用DAG平台。例如改结束日期，库存和预览需要重做；用户身份未变且资格观察仍有效时，不必重新生成整篇政策解释。

依赖表由确定性代码维护，使用字段集合与规则/资源版本。动态库存有时效限制，提交前仍读取当前事实，不能将“少验证”理解为永远复用陈旧库存。用户看到一行说明：“日期已更新，已重新检查可用设备；政策依据未变化。”

这同时改善响应和可解释性。实际节省多少调用以日志比较，不提前承诺数字。

### 8.3 有真实依据的备选方案

没有符合条件设备时，查询规则允许的其他设备类别或用户许可范围内的可用日期；返回有限的可比较选项，展示与原需求的差异及仍需确认的内容。

候选由业务数据查询生成，模型只负责解释和排序理由；若后端没有排期数据，就不编造“下周二有货”。用户选择后更新任务参数并重新生成预览，不自动放宽要求、不预先占用设备。

第一版不需要优化求解器：使用现有库存查询、简单排序和2—3张候选卡即可。其价值来自真实可选，而不是复杂规划术语。

## 9. 前端：聊天、表单、进展与结果在一个工作台

建议沿用HTML/CSS，将长行内脚本拆成模块化JS。选择现有组件和样式实现，当前不增加独立Node常驻开发服务作为默认启动依赖。

任务页布局：左侧最近任务；中间对话和进展；右侧当前参数、预览/备选、来源与回执。窄屏将右栏折叠为页签。

```text
最近任务        当前任务：借用电脑              当前需求
  借用申请       已核对日期与用途                起止日期 [编辑]
  政策查询       正在查询可用设备                用途     [编辑]
                需要你选择一项：                
                [保持日期，选择B设备]           依据
                [保持设备，调整日期]           [制度章节] [查看原文]
                                                
                对话输入 / 附加说明            预览 → 确认 → 回执
```

进度描述来自真实事件，如已查询库存、等待用户选日期，不能播放与后台无关的进度动画。常见错误在当前操作附近给出解释和恢复按钮，不能只在浏览器控制台报错。

历史任务展示的是实际业务结果和可做动作。task_id、原始JSON、源码指纹和详细调用数据不占主界面；开发者详情保持折叠且可选。

用户可以随时返回纯RAG，不强制所有知识问答都创建长期服务任务。工作台统一不等于所有功能被合成一条复杂流程。

## 10. 数据、作业和事件是产品能力，不是新平台

详细契约见`ENGINEERING_CONTRACTS.md`。整体要求是：业务数据库保存事实，run记录一次执行，事件帮助界面增量显示，文档作业记录耗时处理。几个对象各有职责，不在每层都新增一份“完成状态”。

默认本地作业执行器与应用同生命周期，使用有界队列；排队状态持久化，关闭时不继续接新工作，正在运行的任务记录中断/可恢复。不要先加Redis/Celery；未来确有多个worker再替换执行器，而不是改用户任务契约。

事件只是一条普通递增序号流，保存关键步骤与必要结果引用，不把所有模型token和推理过程写入数据库。UI断线后用任务快照和`after_seq`补读，不靠全量重放证明任务完成。

## 11. R2：用第二个服务检验扩展能力

当R1完整可用后，增加**本地合成IT报修**：故障描述、设备、分类、影响程度、联系信息、预览、提交、本地工单编号和状态查询。

其规则文件和数据明确写“演示规则”。不能推断用户真实公司要求，也不能把本地工单写成真实维修审批。当前借用模块中的维修资格数据保持原语义，除非以后明确实现联动，不让报修Demo自动改变借用资格。

通过一个轻量Service Catalog登记字段schema、工具集合、准备/提交/查询适配器和表单说明。公共运行图、任务历史、事件、确认组件不复制。第一种服务先收敛，第二种服务用来揭示真正共性；不提前设计包含二十个空接口的插件SDK。

R2同时接入目录增量导入和反馈。反馈只记录用户指认的问题类型、对应答案/任务与必要备注，形成可重现案例；不为每个问题自动启动多模型评分或声称自我学习了模型权重。

## 12. R3：明确条件触发的长期演进

| 后续方向 | 何时有必要 | 迁移边界 |
|---|---|---|
| PostgreSQL | 多用户并发写/多个应用实例成为实际需求，SQLite限制已经影响使用 | 替换仓储和迁移，不重写Agent/前端 |
| 独立worker/队列 | 解析队列长时间占用服务或必须跨机执行 | 替换JobRunner，保持任务与事件接口 |
| 真正企业身份接入 | 有组织级使用需求和可用认证配置 | 接入既有身份边界，不再写一套用户系统 |
| 外部业务/MCP适配器 | 已确定真实服务及读写契约 | 优先单个读工具和预览适配器，再明确开放写入 |
| 向量库/ANN/重排 | 相同场景测量证明召回或规模瓶颈 | 替换检索适配器，对答案契约不产生连锁变化 |
| 更完整前端框架 | 当前组件规模与交互维护明显成为成本 | 独立迁移前端，继续使用同一API |
| 多Agent | 存在能独立完成、有清楚输入输出和可测收益的子任务 | 先单个隔离试验，不把简单借用改成角色扮演 |

这些不是“现在全部做一遍”。当前Goal只覆盖R1与R2。

## 13. 工程质量与演示：少而有用

质量检查围绕用户旅程，不围绕报告数量。修改哪个模块就跑相关检查；阶段结束从真实入口跑一次，发布时覆盖安装、导入问答、正常借用、改期、无库存/已有申请、重复提交、刷新与重启、第二服务和增量同步。

保留已有关键事务和条件引用反例。不为了过关删断言，也不让无关的历史实验矩阵阻塞每次UI修改。离线fixture检查程序行为，少量实际模型旅程检查集成，两者明确分开。

只测真正能改进用户体验的指标：页面是否可用、首次可见进展、整体耗时、模型调用数、重复工具数、用户必须重复输入的字段数、任务结果和来源是否可打开。模型耗时/排队/检索分开看。没有基线不预设提速百分比。

提供一个真实产品演示：导入合成资料→问政策→转借用→修改日期→比较备选→确认→读回→重启继续；再展示IT报修复用同一工作台。演示不依赖预录JSON冒充实时运行，也不为了每天演示重复调用整套模型测试。

## 14. 最后明确取舍

我们接受单体暂时不具备多机高可用，换取启动与维护简单；接受业务状态级恢复，而非任意token级续写；接受先使用现有检索技术，而非立刻追逐GraphRAG；接受先将页面组件化，而非同步重写整个前端。

同时不接受用户启动失败只能读长日志、不接受改一次日期就重跑所有理解、不接受静默丢参数、不接受只能看测试结果不能操作产品。这些是本次重构必须真正改变的部分。
