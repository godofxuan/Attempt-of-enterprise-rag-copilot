# 一轮完成的bug修复、UI美化与代码收敛

## 一、目标与非目标
### 目标
用户在同一工作区中能够轻松打开应用，知道当前状态和下一步，完成知识问答、文档管理、借用和报修；失败或正常缺信息时不用猜怎样恢复。维护者能在少数明确模块找到规则，不需要追多份状态和重复错误处理。

### 本轮不做
不新增第三业务、多Agent、长期记忆、插件市场、流程画布、向量库迁移、数据库迁移、第二套前端、桌面框架迁移、全树哈希/报表系统。不开新解释语义实验。不为追求行数或测试数量机械拆文件、删判断。保留必要身份范围、精确确认与幂等，不向外增加更多层。

### 结束方式
完成本文件8项工作及12类验收的必要部分后，交付一个0.7收尾版本。根据当前仓库版本取rc3或合适补丁名，不自行开启0.8目标。未验证Windows时可交付明确预发布候选，但不能声称已完成稳定Windows验收。正常修复完成即可推既有授权feature分支，不等待实验功能转正。

## 二、先修两个可定位问题
### 2.1 把“保存参数”和“形成预览”拆成两个结果，不增加两套流程
当前一次mutation承接多个服务调用，第一步已经产生持久结果，却由第二步的失败决定整体UI。这是本轮优先修复的状态一致性问题。

建议顺序：
1. 保存当前草稿，明确携带基于哪个revision编辑。
2. 服务端成功即使用其响应更新当前task、revision与草稿基线，显示一次“已保存”。不要等prepare成功才承认保存。
3. 根据实际状态执行下一步。字段缺失则留在表单；需设备则展示候选；满足条件才准备。
4. prepare成功更新preview；prepare失败仅报告准备阶段失败，并保留第一步结果。
5. 仅刷新该事项、关联会话和必要列表。异常情况下也要同步已提交的前序修改，但不要无条件全局刷新所有查询。

用户文案：
- “用途已保存，请选择设备。”
- “日期已更新，原预览已失效，请重新查看当前预览。”
- “参数已保存，暂时无法读取库存。重试库存查询。”
不显示笼统“保存失败”或要求重复提交相同表单。

实现放在现有TaskDetail和API hooks中，提取具名saveFacts/prepareTask操作；不要继续给万能mutation增加更多`prepareAfter`/`continueTask`布尔选项。兼容既有HTTP接口，不为了UI修复复制业务规则。

### 2.2 等待用户不是系统故障
统一一个纯粹的下一步视图投影，输入现有task/run/delivery，输出已有页面可消费的state label、primary action、必要字段或候选。不再持久化第三套状态机。

优先顺序：
| 实际情况 | 主状态/动作 | 不该发生 |
|---|---|---|
| 当前run仍运行 | 正在处理；允许停止本次运行 | 同时“继续”“重试”“生成” |
| 尚缺必填信息/真实歧义 | 待补充；聚焦对应字段 | 覆盖成BLOCKED或空转重试 |
| 需要选择设备 | 待选择；展示真实候选 | 先报错，再让用户找折叠菜单 |
| 可用预览已形成 | 待核对；按原范围确认或仅查看 | 用知识回答成功替代提交确认 |
| 一部分结果失败 | 已保存部分结果；只重试失败项 | 重做已成功提交 |
| 单据已存在 | 当前单据状态与合法后续动作 | 重开新申请 |
| 事项已关闭/取消 | 查看历史；会话可继续 | 为重试解释重新打开已取消业务 |

waiting_input不意味着让用户绕过必填项；明确动作不能超出已选范围。所有视图使用同一个投影，避免API、Agent收尾、React分别猜测。已有Run/Turn/Task结构保留。

## 三、美化应落实到可读、可行动，不另画一套空原型
### 3.1 保留当前品牌和三入口
继续“助理 / 我的事项 / 资料库”，设置与本地合成服务台保持次级入口。继续单输入框和详情抽屉，不建设双聊天框或新仪表盘。使用已有组件原语和React/TypeScript，不新增组件库来替换功能类似的现有实现。

### 3.2 统一视觉tokens
建议目标（设计参数，可在实际屏幕微调一次后冻结）：
| 项 | 建议 |
|---|---|
| 基础正文 | 15px；聊天正文15–16px；行高1.65–1.8 |
| 主要说明 | 13–14px；10–11px仅留给非关键元信息 |
| 标题 | 页面24–28px，分区18px，卡片15–16px |
| 主文字/次文字 | 深灰/中灰；重要说明不使用近背景色 |
| 色彩 | 沿用当前绿色强调色；白卡片与浅灰背景；状态不只靠颜色 |
| 间距 | 4/8/12/16/24/32px，删去零散随意值 |
| 圆角 | 输入与按钮8px，卡片/抽屉12px左右 |
| 控件 | 桌面高度约40px；手机主操作触控区域约44px |
| 内容宽度 | 聊天约760–840px；工作页最大约1120px |
| 抽屉 | 桌面约440–520px，手机全宽，不叠第二层全屏详情 |

普通文本对比度目标至少4.5:1；遵循W3C说明，不宣称仅修改颜色就完成全部无障碍认证。避免外部字体下载。保留系统中文字体。

### 3.3 助理页
- 标题与资料范围放在同一工作区；连接状态一个小入口，不在顶部重复堆多个告警。
- 首次空态给一项最适合的动作：连接模型/导入资料/开始提问。不要所有新手提示永远显示。
- 消息按“直接结果 → 必要条件 → 来源”组织；来源默认小按钮或折叠区，业务JSON不进入正常正文。
- 只保留一个输入框。Enter发送、Shift+Enter换行，composition期间不发送；实际中文输入法最终确认一次。
- 运行时显示可理解阶段，无token级日志；用户已向上阅读时不强制滚回底部，提供回到最新。
- 保存草稿到当前会话身份下；切换不会把A草稿放到B。若已有实现通过，保留而不是重新写。
- 错误卡紧贴受影响回合，包含“已完成什么 / 未完成什么 / 一个下一步”。不要Toast、红条、抽屉三处重复错误。

### 3.4 事项详情与我的事项
详情纵向顺序：当前结果摘要 → 必须补的信息/选择 → 预览或当前单据 → 来源 → 更多详情。
同一阶段仅一个主要CTA，必要时1–2个次要操作。保留所有业务动作，只按状态呈现；归还、续借、重开等不得为简洁而删除。

设备卡突出名称/内存/取用地点/可用日期。需要选择时自动展开并聚焦候选区域，不让用户先触发错误。选择后同一用例准备，不复制前端规则。
表单清楚区分未保存草稿、已保存字段、失效预览；保存后不保留旧revision。既有版本冲突发生时显示最新值和用户草稿，不能自动覆盖另一页修改。

列表卡只展示：事项名、当前业务状态、关键日期或设备、最近更新、下一步。task_id、命令ID、hash收进开发详情。可查看提交时回执和当前状态，但用人话说明二者不同。

### 3.5 资料库、设置、服务台
资料库：上传区域、处理状态、文档列表分区；“已上传/正在解析/正在索引/可问答/失败”明确区分；失败定位该文件而不是覆盖整个库。批量、版本、停用、目录增量等现有能力保留，低频操作收进更多菜单。新资料处理中，说明当前可查询范围，不静默用错版本。
设置：当前工作区、模型连接、已安装模型、版本信息分组；高级超时与实验项折叠。已关闭实验解释保持关闭，不在首页承诺新能力。
服务台：明显标记本地合成演示；只展示当前单据能做的真实动作。审批、领用、归还、处理、关闭均调用真实业务API，不使用页面固定成功数据。

### 3.6 键盘和窄屏只做必要收尾
复用现有Dialog的焦点圈定、Escape和关闭返回触发点；不要重写焦点框架。确保固定底部输入框不会遮住最后一张卡；长文件名、中文长句和表格可换行或区域滚动；390px下没有整页横向滚动。减少动效偏好时关闭非必要脉冲/过渡。

## 四、代码简化：消除重复责任，不把错误藏起来
### 4.1 允许修改的核心范围
- `runtime/turn_coordinator.py`：waiting与partial的归属、结果收尾。
- `service_desk/views.py`与现有Product DTO：统一展示状态/next action。
- 当前`TaskDetail.tsx`及相应hooks：保存/准备分别处理成功与恢复。
- `api/client.ts`、Query keys与现有事件hook：错误分类与定向刷新。
- `style.css`和现有页面组件：视觉tokens、CTA、表单与来源显示。
- 启动器与打包只修实际验收暴露的问题，不更换技术。

### 4.2 状态只保留最少必要信息
服务器负责业务事实与revision；Query缓存服务器响应；组件仅负责未提交草稿与展示开关；URL标识当前会话/事项。能从现有对象计算的按钮状态不再另存一个布尔状态。遵循React官方避免重复和矛盾状态的原则。

### 4.3 具名操作替代布尔组合
优先拆开当前万能mutation的save/prepare/select/confirm/retry等动作，每个动作调用既有API与领域服务。页面只组合用户步骤，不重新写规则。可用少量联合类型表示ready、needs_input、needs_choice、retryable_error；不以通用工作流引擎代替简单类型。

### 4.4 数据获取与错误处理
写成功即更新其结果，不依赖后续操作成功。按照TanStack Query已提供的mutation响应更新和定向失效机制，刷新task(id)、关联conversation、必要列表；只有库目录或全局设置变化才刷新相应全局查询。不要每次onSuccess都清空所有Query。
期望内的业务分支用清楚的操作结果呈现，真正故障保留错误。既有HTTP409适配可保留，不为了语义整齐破坏旧接口；统一一处将错误码和结构化data映射为用户动作。

### 4.5 不做机械缩行
对本轮触及文件统一格式、删除重复逻辑、合并相同映射。不是把多行if压成一行、用嵌套三元制造“简洁”、建立巨大BaseManager或到处catch Exception返回成功。
Store已有事务保留；不把一次写入拆散。不仅为了大文件行数迁移整个Store/ORM。确认无产品依赖的旧Web或实验模块可收窄发行范围，但暂时不能确认的历史内容留档，不把清理完成率当门槛。

## 五、功能不减的保存清单
| 功能族 | 必须保留的可见出口 |
|---|---|
| 知识问答 | Fast/Deep、追问、来源、历史、不足说明 |
| 资料管理 | 上传/批量、解析索引、重试、版本、停用、目录同步 |
| 会话 | 唯一输入、历史搜索分页、草稿、切换、失败重试、停止 |
| 借用 | 补充、选择、改期、预览、一次确认、提交读回、审批、领用、续借、归还、再次申请 |
| 报修 | 缺字段补问、预览、提交、处理、解决、关闭、重开 |
| 应用 | 模型未就绪可开页、固定工作区、实例复用、版本识别、重启历史 |
| 数据约束 | 身份范围、revision、精确确认、事务、幂等、来源版本 |

功能藏进合理的二级入口可以，但不能取消能力、改成固定结果、跳过真实查询。旧数据能用比新增一套更整齐的空数据库重要。

## 六、8项工作与顺序
详见work_items.jsonl。三批合并：先W01–W03修正确性；W04–W06美化与局部收敛；W07–W08验收与发行。视觉tokens定稿后统一页面，不每一页重新发明样式。

## 七、避免无休止的规则
1. 只对本轮范围内、或阻塞现有功能的实际问题立即扩展修复；未来愿望进backlog。
2. 不为计数补测试，不复跑不受影响的完整模型矩阵；保留现有有效回归。
3. 同类补丁连续两次无进展，回到共同调用链和状态归属；不要追加关键词和超时。
4. 没有足够证据认定的风险标待确认，不自动升成必修大项目。
5. 修复与设计验证直接在实际页面完成，不再交付另一个静态原型充当产品。
6. 范围内功能正确、页面清楚、最终包可用且必要验收完成即结束。非关键美化差异和实验模型质量不阻塞默认版。
