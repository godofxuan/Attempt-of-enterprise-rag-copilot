# 0.3 / 0.4 产品升级设计

## 1. 本轮目标

从“能完成合成借用/报修演示”升级成**会话驱动的企业知识与服务工作台**。

同一会话里能够问资料、补信息、修改参数、比较真实资源、查看预览、确认办理和继续查询；服务台视图能把本地业务从待处理推进到完成。文档与业务互相解释，但答案不自动改写可执行业务规则。

三个优先方向：
1. **可持续的会话与任务体验**：一条消息不只会改字段，运行能停止/继续，动作卡和当前状态清楚。
2. **真正的知识能力**：快速问答、分题深入检索、来源定位、业务内解释和资料生命周期。
3. **可长期演示的完整业务产品**：处理台、资源排期、归还/关闭后再办理、第一次使用与发布。

0.3完成前两条；0.4完成第三条与整体验收。不是只修3个bug后停止。

## 2. 架构决定

继续一个Python/FastAPI应用、一个当前数据目录、SQLite和Ollama；页面随Python包发布。不新增常驻Node服务、Redis、Celery、独立向量数据库或多Agent平台。

结构上分四个职责，而非四个部署服务：

```
ConversationService  — 接收一句话、维护回合与当前关联任务
      │
TurnRunner / ContextBuilder / ToolCatalog
      ├─ KnowledgeService（共用检索/证据/生成）
      └─ DomainServices（借用、报修、处理台、资源）
      │
RunLifecycle + ProductEvents + SQLite
      │
会话时间线 / 当前参数与候选 / 来源 / 预览与回执
```

### 2.1 默认保留现有原生工具循环

没有证据要求为了名字迁回LangGraph或接入完整Deep Agents。学习Deep Agents的模型/工具/middleware装配与运行时分工，不照搬默认文件、子Agent、shell能力。将当前循环内部的数据装配、工具映射与终态整理成三个清楚模块即可。

### 2.2 业务状态和执行状态分开，但只各有一个所有者

- conversation保存用户与助手的回合；它不是业务数据库的替代。
- task是一次具体办理意图与当前参数，允许关联不同回合。
- run是一次执行。停止run保留task；结束task不等于撤销已经产生的ticket。
- ticket是业务事实，申请提交后仍可演进。旧receipt是提交时快照，旁边另显示“当前业务状态”。

不新增第三套“case truth”。产品里可以叫“事项”，实现上优先使用现有task/ticket/conversation关系。

## 3. 主线一：统一会话、动作卡与连续办理

### 3.1 用户可以说完整的话

应支持以下典型回合，不靠预设题号：

- “我电脑要送修，先看能不能借备用机。”——读政策/资格/资源，给出解释；不直接提交。
- “从下周一借到周三，主要拿来调试程序。”——补充字段并继续准备。
- “结束日期改到周五，再告诉我是不是要交押金。”——同一回合更新草稿＋查询知识，返回两部分结果。
- “这台内存不够，换一台至少16GB的。”——把偏好传给资源查询，给出真正符合条件的候选。
- “为什么不能办？”——解释当前实际业务原因和对应规则，不把它当用途修改。
- “先停一下。”——停止正在运行的run；随后“继续”基于已保存事实恢复。
- “我上次的报修现在什么状态？”——查真实ticket，已提交任务也可以在会话里继续询问。

### 3.2 不是新增一个永远先跑的“意图分类Agent”

明确UI动作（改日期、选择资源、确认、停止）直接进入确定性API。自然消息由当前主模型结合上下文选择工具或返回答案，必要时产生一个小型结构化TurnPlan：问题、字段变更、需要的读取、待澄清项。

不要每轮固定“分类→理解→规划→重写→review”。能一次主模型调用处理的，保持一次。当前ParameterChange可复用，但不能作为所有消息的唯一返回格式。

标准Pydantic校验字段、类型与业务约束；保留原文及可选引用片段便于解释。允许正常相对日期和语义整理，不继续增加关键词白名单或要求所有标准化值都逐字出现在原文中。有歧义只问一次具体问题。

### 3.3 ContextBuilder必须告诉模型当前真实情况

包括当前消息、最近相关回合、task的当前facts、已选资源、当前ticket状态、仍有效的观察和已绑定知识摘要。

历史助手答复可以作为对话指代背景，但不能直接当权威知识证据；需要时用它指向的source再次读取。旧日期和过期库存不能混进当前事实。按token预算裁剪重复tool JSON，不每轮加一个模型做压缩。

当前默认8192上下文与1024输出不作为所有任务永久硬限制；以实际模型能力配置fast/deep/action三种请求预算，只有一份设置源。同时调整证据打包预留和实际HTTP参数，避免再次出现二者不一致。不是单纯无脑加长输出。

### 3.4 对话输出是“说明＋可点击对象”

助手回合可包含：自然解释、来源、当前参数变化摘要、资源候选、待补字段、预览、实际回执。动作来自服务目录和当前业务状态，不把模型任意文本变成操作按钮。

来源回答中的“继续办理”按问题和当前支持的服务提供真实选项；会议室制度不能永远只展示“开始借电脑”。相关但未实现的服务可以不显示动作，不能冒充已经接入。

### 3.5 UI从控制台改成工作台

左侧按标题和更新时间展示会话/事项，不主要展示随机task ID。
中间显示实际对话、进展和结果。右侧显示当前参数、候选、来源与预览。数据仍从后端TaskView取得，不在前端另造规则引擎。

保留现有HTML/CSS基础，先拆成api/events/conversation/tasks/library/renderer模块，统一一个小的页面状态管理与事件清理。不要为了漂亮引入整个平台。

保存字段或完成自然变更后自动执行受影响的只读步骤和重新预览；正式提交仍一次明确确认。普通查询和参数保存不再额外要求范围复核。JSON与调试事件折叠，错误说清楚可做的下一步。

### 3.6 运行事件与流式体验

借鉴Dify的后台事件到应用事件映射。前端只消费少量事件：started、progress、text_delta、sources、field_changes、needs_input、preview_ready、receipt、finished、failed、cancelled、interrupted。

Ollama流式工具调用先累计完整参数再执行工具；未结束JSON不能触发操作。现有结构化答案若不适合逐字发布，先流式进展与已完成结果块，不为了首字速度把未发布正文冒充正式答案。

断流后按cursor/Last-Event-ID重连和读取快照；全部终态都释放按钮和EventSource。取消当前run不关闭事项，不依赖重启解锁。

## 4. 主线二：知识检索成为真正的共享能力

### 4.1 同一结果核心，两个检索策略

继续复用EvidencePacket、AnswerResponse和现有正式publisher。检索策略不同，不复制另一套答案和引用schema。

**Fast**：对当前独立问题或经必要指代消解的问题进行混合检索，RRF、去重、必要的段落扩展，一次主要回答。能直接答的就结束。

**Deep**：只在用户选择深入或明确跨资料复杂问题时启用：
1. 生成少量有目的的子问题（建议2—5，不作为固定强制数）。
2. 以子问题分别检索，保留来自哪项需求、哪份文档的命中。
3. 合并相邻片段；选定文档后按需read/find，寻找缺失条件与版本差异。
4. 形成短证据表：问题、已找到的证据、冲突或缺口。
5. 使用同一正式答案契约给出结论、比较表与来源；到有界预算仍缺就具体说明。

工具数量不是深入程度。不要把max_search_calls调高就宣布完成，不为所有问题固定多模型规划链。只并行独立读取；变更和提交仍按业务先后顺序。

### 4.2 业务任务中也能访问知识

loan/repair的工具目录加入只读知识查询与来源读取，复用KnowledgeService。Context中明确当前服务关联的知识库、原答案ID/来源版本和用户真正的问题。

已关联的正式答案仍有效时直接复用；问题、来源或版本变化时重新查询。不要“完整生成一次→拼成文本→再拆引用→再review”。

**文档知识与可执行规则不能默默混同**：业务资格/日期上限等仍由配置明确的DomainRule执行。来源制度与规则版本有可查绑定；发现不一致，解释冲突并提供设置入口，而不是让模型决定哪个约束不算数。演示规则由同一结构化定义生成可阅读示例文件，减少手工写两份后漂移。

### 4.3 来源定位真正穿过解析/分块/索引

文档元数据保留标题、集合、类型、版本、可选生效时间与服务标签。不要把所有资料都伪装成effective_from=2000-01-01的policy。

定义/扩展现有chunk metadata的SourceSpan：document_id、version、parser section/path、原页码或段号/表格、文本偏移。切块可跨多个span，引用绑定实际span。页面打开相关位置，而不是把整本PDF解析文本和所有locator一次吐给用户。

复用现有PDF/DOCX解析器。没做OCR就诚实显示无文本，不强行扩展到所有复杂文档。

### 4.4 文档生命周期补完整

支持批量上传、解析失败重试、重命名显示标题、停用/恢复、版本对比与索引状态。停用不物理删除历史引用；恢复后按活动版本重新构建。用户目录缺文件的处理保留明确策略，可选提示后停用，默认不静默抹掉。

上传后可自动排队更新索引或提供一个清楚的“使资料可问答”操作；不要依赖用户猜测PARSED不等于可检索。后台显示阶段和数量，中断可继续复用现有embedding缓存。

### 4.5 优化优先依据真实开销

先区分解析、索引、检索、模型加载、prefill和生成。embedding由目前逐chunk HTTP发送逐步改成批量发送＋缓存命中，复用Ollama已有批量input。避免一边引用小样例缓存收益，一边忽略大文档串行往返。

不要先换数据库/向量库或新增reranker。只有实际语料表现出排序瓶颈，再将已有reranker作为可选项进行同场景比较。

## 5. 主线三：申请之后仍有系统可用

### 5.1 保留本地演示边界，但把业务做完整

新增“本地服务台处理视图”，明确是合成系统的操作视角，不冒充真实企业授权。它调用真实DomainService/SQLite事务，不通过修改数据库脚本伪造演示。

借用建议状态：PENDING_APPROVAL → RESERVED → CHECKED_OUT → RETURNED；另有REJECTED、CANCELLED。批准与实际预留若采用同一动作，必须确实在事务内建立预留记录，不能仅把标签改成approved。

报修建议状态：OPEN → IN_PROGRESS → RESOLVED → CLOSED，必要时支持明确重新打开。每个动作可有说明和当前可用操作，用户页面读到真实状态。

0.4必须有“原数据目录中申请→处理→归还/关闭→再次申请”的体验，不再以新建TEST目录作为正常循环使用方法。

### 5.2 资源从available布尔值升级为日期可用性

保留资产静态信息：规格、位置、启用状态。新增预留/占用区间，按资产和日期查询冲突。UI日期含结束日时，内部统一转为半开区间[start,end+1day)，文档明确时区和口径。

正式预留与状态更新在同一SQLite事务中检查冲突。用户只是在预览时不能占住设备。取消/归还释放相应预留；历史记录保留。

保留现有每人未结申请约束，除非明确修改业务规则；不能因为扩充资源计划就静默取消原业务规则。

### 5.3 候选方案真的解决约束冲突

字段允许明确设备偏好，例如内存下限、位置、日期灵活性。DomainService从实际资产与区间数据产生2—3个候选，说明匹配、差异与代价。模型负责解释，不生成不存在的库存。

只有用户允许日期灵活时才建议相邻可用时间；每个候选是可选择的新参数，不自动替用户修改或提交。

可加入前提交草稿修改、待审批撤回和借出后的续借申请。所有变更沿同一ActionSpec/preview/confirmation/command/readback机制，不写第二套事务。已经提交后的参数不能直接patch原receipt。

### 5.4 共享能力从第二服务验证，不先加十种业务

将字段、缺失提示、工具、状态、可执行动作和结果组件逐步收拢到现有Service目录。Loan与Repair实现自身规则，其余任务/会话/事件/预览机制共用。

当前报修工单不自动修改历史借用资格的repairs表。若增加报修→借用资格联动，必须显式配置一个来源适配和可见关联，不凭“都是repair”偷偷同表或自动联动。

## 6. 实施中的代码职责

这不是要求一次创建全部空文件。随着每条功能落地逐项抽取：

| 当前代码 | 目标职责 |
|---|---|
| `workspace.py` | app workspace装配；按settings/library/conversation/tasks拆router |
| `workbench_service.py` | TaskService调用领域服务；messages进入ConversationService |
| `workbench_agent.py` | 薄循环；ContextBuilder和ToolCatalog分别抽取 |
| `service_desk/catalog.py` | 唯一服务字段/动作目录，避免QUESTIONS等平行字典 |
| `service_desk/store.py` | 逐步分离TaskRepository、ProposalService、TicketService；原事务核心先复用 |
| `workbench_knowledge.py` | LibraryService、KnowledgeService和索引作业明确边界 |
| `runtime/workbench_runs.py` | RunLifecycle统一终态、事件与继续入口 |
| `web/workbench.js` | 单页面应用的小模块：api、events、threads、tasks、library、renderers |

不要并行运行新旧业务实现再新增仲裁器；旧API可以是薄兼容适配，默认入口只有一套。

## 7. 首次使用与发布

启动仍使用现有esa CLI，不重新发明复杂launcher。第一次进入页面时配置本机模型、选择是否建立合成示例、导入资料并显示可用状态。`init --sample`保留幂等；示例文档作为包资源，wheel也能获取，不依赖仓库examples路径。

doctor不要提前加载历史RAG容器，普通工作台启动也不装配不用的legacy API。保留旧API在显式legacy入口，而不是删除旧有效资产。

模型选项来自已安装列表，明确冷热启动和连接错误。不自动下载大模型；不会把真实模式失败自动替换为fixture。

项目README以当前版本的安装、配置、能力和演示为主；历史作品集记录移到单独历史文档，链接指向可到达的版本。发布源包/wheel都在干净目录按同一说明检查；不再产生多个版本互相冲突的交接包。

## 8. 不做的事

不建AgentOps平台、哈希台账、权限研究、多模型judge链、复杂审批树、泛化插件市场或分布式任务集群。现有内容hash用于文档去重/cache、预览快照用于正确提交，这些有实际用途，不必机械全删。删的是没有用户收益的重复证明与默认运行耦合。

完成目标以用户能连续用完产品为准。模型名字、代码行数、测试数量、Star数都不是完成标准。
