## 3. 五个已复现缺陷、一个源码风险

### F01 / P1：重试丢失原请求，Deep静默变Fast

位置：`app/api/product_routes.py:73–88`。重试只重建conversation_id、text、message_id，没有保存detailed或原知识/任务绑定。本次外部知识函数实际接收到 `[true,false]`：第一次Deep失败，重试变Fast并成功。

改法：用户回合保存原始不可变请求；attempt引用它，不重建用户意图。deep、知识范围、选中来源、已绑定业务事项等由请求保存，当前业务事实另行读取。不能为了重放旧请求把用户后来修改的日期覆盖回去。资料/任务已失效时返回具体的重新选择入口，不偷偷改模式或改绑定。

验收：Deep失败一次后重试仍Deep；同一原回合只有新的attempt，不多写用户消息；恢复后没有重复业务写入。

### F02 / P1：无知识库时建的会话无法恢复，界面还可能显示虚假的选择

后端：`app/conversations.py:280–299`要求stored kb_id；当前没有绑定更新路由。实测先无KB建会话、失败、再创建KB、重试仍 `KNOWLEDGE_BASE_REQUIRED`，知识调用次数0。

前端：`frontend/src/features/Assistant.tsx:142–148`用 `conversation.kb_id || base || firstLibrary`显示选择，但已有cid时禁用。这意味着界面可显示第一个库，服务器实际上是null。

改法：允许明确给既有无绑定会话选择资料库，再从同一回合继续；若允许后续换库，应对新回合记录范围，不能改变旧答案出处。纯业务任务不需要强迫先选知识库，知识问题缺库时给出可操作引导。字段真值与显示一致。

### F03 / P0：登记目录移走后，启动器悄悄创建空工作区

位置：`app/launcher/core.py:36–43,59–80`。选中登记路径后无条件mkdir，workspace.json不存在就initialize。

实测：初始化有会话的目录→登记→将目录移动→启动。原路径重建空库，新实例会话列表为空；原数据仍在移动后的目录。**没有证明数据被删除；这是关联丢失和误初始化。**

改法：区分用户明确新建、打开已有、查找丢失。登记路径缺失/不完整时给出“定位原工作区 / 明确新建 / 退出”，绝不静默初始化。沿用现有lock和实例复用，不通过杀别的进程解决。

### F04 / P1：100条以后的历史在界面不可找回

位置：`app/conversations.py:148–154`固定LIMIT100；前端搜索仅针对已经返回的列表。实测建105条，列表100条，最早记录不在列表但详情HTTP200。是不可发现，不是数据丢失。

改法：服务器端游标分页与标题/必要文本搜索，按稳定(updated_at,id)排序；UI更多真正请求下一页。复用当前索引能力即可，不引入向量库来检索标题。

### F05 / P1：活动run在前端不是按会话归属【源码确认；浏览器未复验】

位置：`Assistant.tsx:34–35,60–80,256–282`以及App的全局事件。sessionStorage用单一esa-active-product-run，切换cid不清除/改派归属，stop按钮使用该runId，发送按钮受它限制。

风险：A运行中切到B，B展示/停止A或被A无理由阻塞。后端已有按conversation取runs入口，不需要再造前端全局任务总线。

改法：run的conversation/turn/attempt归属明确；页面从当前cid对应服务器runs恢复状态；事件按owner更新Query缓存；取消请求指向明确run。模型可以全局排队，但队列归属必须显示正确，不能把A伪装成B。离开页面仅结束订阅，不自动取消业务。

### F06 / P0：预览成功被当作整轮完成，漏掉用户另一项请求

位置：`app/agent_runtime/workbench_agent.py:276–285`。成功prepare_preview后直接return。

本次原业务探针：用户“先准备预览，再解释押金；不要提交”；脚本模型第二批同时提出prepare_preview和knowledge_answer。预览真的创建，但knowledge_answer完全未调用；knowledge_result为空；用户turn标DONE；没有提交。

这是执行器的短路，不能归咎模型不会规划。改法不是盲目继续全部工具：保留已生成的预览结果，执行仍然必要且无副作用的知识读取；若后续有参数修改，先失效旧预览并重新准备。整轮结束按交付结果，而不是某个工具名决定。使用小型typed outcome集合和当前工具批次即可，不新增完工judge Agent。保留显式确认提交。

## 4. 知识质量：摘录完整不等于回答完整

`generation_v2.py:193–217`要求逐source unit的unit_uses映射；`1154`明确最终正文只能由选择的完整原文单元组成。这个设计降低原句被改坏的风险，但限制解释、条件推导和跨文档比较，也增加模型对每个候选单元填表的负担。

提交的七例“核心通过”主要以关键字符串、来源和mode检测。Deep两文档结果是两份规则原句连列，并不等于完成有组织的差异比较。缺失信息例在中文会话返回英文固定句。附件也明确保留长首问空选择、假设资格过于保守的失败。这些是提交的真实模型记录，不是本审核新增模型运行。

建议：同一AnswerResponse中支持有依据的答案块与引用，证据原句在详情保留，原文模式继续可用。不要用第三套writer/协议，也不加每轮语义审判。引用合法的确定性校验≠语义成立，应由小而完整的离线语义评测发现问题。

## 5. 仍需完成的产品工程

- 当前构建脚本依赖 `.venv/Scripts/uv.exe`和已准备的runtime路径；实际有可用包，但还不是任意干净Windows目录都能重建全部依赖的闭环。补构建编排，不换启动技术。
- 浏览器脚本硬编码msedge、8740和个人工作区输出路径；需要标准Playwright测试入口与临时工作区，不应让回归修改活动数据库。
- `app/knowledge/query.py`检查文档集合/元信息与当前索引一致，更新期间的知识可用性还应做场景验证。此项作为设计改进，不伪称已经复现数据损坏。
- 前端已生成OpenAPI类型，但业务代码仍大量用JSONRecord/字典；优先让常用任务、工具、知识结果用明确类型贯穿，减少同一格式的猜测分支。
- 本轮不建议再扩第三业务、多Agent、长期记忆、第三份后端，或更换SQLite/FAISS。
