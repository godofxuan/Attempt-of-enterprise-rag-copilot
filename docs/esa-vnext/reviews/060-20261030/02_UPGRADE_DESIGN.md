# 下一轮完整设计：恢复正确、完成完整、知识可用

## 1. 产品目标与保留清单

把0.6预览变成“反复打开、反复使用、不依赖开发者善后”的本地企业助理。先交0.6.1可靠性修复，再在同一主线交0.7成熟使用版。不要把上一轮已经完成的React、Deep、业务后半程重新当作待造功能。

保留单FastAPI、React+TS+Vite静态发行、薄Windows启动器+内嵌CPython、SQLite、Ollama/BGE-M3、FAISS+BM25/RRF、现有KnowledgeService、原生工具循环、领域事务、预览确认、申请读回与本地服务台。不是强制迁回LangGraph，也不是接完整Dify/Onyx。页面不重画一套，围绕当前结构修交互和状态。

## 2. 共同机制一：用户请求不是一次执行的临时参数

现在回合、run和业务任务已经存在，但原始请求选项与归属仍会丢失。优先扩展现有turn持久化/关联的原始run输入，不另造一套事件溯源账本。

建议最小请求对象（字段名可贴合现有代码）：

```text
TurnCommand
  id / conversation_id / original_user_text
  detailed: bool
  knowledge_scope: kb_id + optional selected_source_ids
  task_binding: explicit task_id or none
  input_mode / explicit user operations
  created_at

RunAttempt
  id / turn_id / status / timestamps / error
  existing trace reference / result references
```

请求表达用户当时的意图；运行尝试表达这次怎么执行；领域数据表达业务现在的事实。三个职责不能混在一起。

### 重试语义

失败重试复用command，创建attempt。保持Deep、知识范围和绑定，不再次根据当前侧栏推断用户原意。读取最新业务状态后决定继续、需要重新确认、还是已办完；不重放所有历史副作用。用户改知识库属于显式修改后派生的新command或确认后的补全，并与原失败回合关联；不能偷偷覆写原历史输入。UI仍可以把它呈现为“选择资料库后继续”，不强迫用户重新输入。

如果索引或文档已更新，不强制重试不存在的旧版本：保留原选库意图，选择当前有效版本并说明变化，历史答案来源仍不改写。精确时点回放属于测试和复现，不是日常必须的复杂功能。

### 归属和并发

使用现有conversation-runs接口或细化它，响应包含conversation_id、turn_id和attempt。React query key包含实际数据身份；按owner订阅进展。A结束的事件不能清空B的run。多标签页刷新都从服务器恢复归属，不以单个sessionStorage值作为真相。

小模型可以继续通过已有并发限制串行执行。B可显示“已排队”，不必为了并发UI增加模型并发数；停止B不能取消A。切换页面只关闭客户端订阅，显式停止按钮才请求取消对应run。

## 3. 共同机制二：业务里程碑不等于本轮诉求完成

保留原轻量循环，但移除“看到prepare_preview成功就return”这类对工具名字的完成特判。

### 推荐执行结构

```text
接收TurnCommand
→ 读取当前业务与会话事实
→ 主模型给出本步答复或工具批次
→ 按依赖与已有规则执行工具
→ 累积本轮可交付结果
→ 还有已提出但未完成的必要读取：继续
→ 需要用户选项/确认：把已取得答案和预览一起交付
→ 真的被阻塞：准确呈现已完成和缺失部分
```

结果采用少量现有类型组合：Answer、Options、Preview、Receipt、NeedInput、Error。给当轮记录哪些结果已获得，未做项与原因是什么；不引入长串任务树和第二个“完成审核模型”。自然输入的目标可由同一主模型已有一次工具决策输出携带，明确页面动作直接生成目标；不可用押金/日期等关键词枚举全部需求。

### 工具依赖不是一律并行

read-only查询可以在不依赖最新变更时复用或有限并行；参数更改先执行，基于旧参数的观察和预览需失效。批次[preview, knowledge]应保留预览并取得知识；[knowledge, preview]也应交付两者；[preview, change_dates]必须更新后重新准备，不能显示旧预览。当用户只要求预览时，生成后即可返回，不额外强制一轮模型。

确认提交仍由确定性业务API执行。知识答案成功不意味着业务可写、审批通过或库存被预留。这个边界保留一次，不在每层重复审核。

### 中途停止和部分结果

收到停止，统一attempt/turn终态；已经提交的单据不能通过停止“撤回”。已经有政策答案但预览失败，可以展示政策和失败入口，不把整次文字吞掉；预览已有而知识失败则标“预览已准备，解释暂未完成”，允许重试知识部分。所有副作用继续使用现有业务幂等标识。

## 4. 共同机制三：证据支持的表达，而非只复制原句

### 4.1 统一知识产品契约

继续扩展现有AnswerResponse和EvidencePacket，不新建并行第3种答案协议。建议增加可选结构化answer_blocks/claims，让每块包含主张文字、supporting_source_unit_ids及必要的条件/局限；source对象仍由程序映射文件版本、页段与可打开位置。

普通模式输出“结论—条件—依据”；Deep输出按比较维度组织的表格或段落、共同点、区别、无法比较之处。需要查原文时保留原文模式，原source unit原句在来源抽屉展示。旧历史答案按原数据渲染，不后台改写。

源ID有效、可访问与出处匹配可以确定性检查；但不能说“引用存在即语义被证明”。金额、期限、否定、例外、主体范围等通过合理prompt、完整证据与离线质量集约束。必要条件满足不等于所有资格足够；材料没写押金不等于免费。材料冲突就列出冲突，不无依据择一。

### 4.2 缩减模型填表负担

将“每个候选source unit都要输出一个字段”的密集映射改为实际使用单元的稀疏引用。保留need的可选覆盖信息，但不要让模型为大量无关来源生成空列表。给模型精简来源，给UI完整元信息，参考Onyx的两种视图思路。

当前8192上下文、1024输出等设置仅是候选配置；不要为了过测试把所有上限无限抬高。按模型支持的token估算组织上下文，记录系统、schema、历史、证据占用。找不到精确tokenizer时标明估算并保守留余量，不把UTF8字节数声称成精确token。

长首问先用同一次生成的结构化输入/提示模板突出问题与约束，必要时有明确长度预算的压缩；不截掉用户末尾的真实问题，不引入每轮固定额外意图模型。假设问题区分给定前提、规则推导与待查事实。未知信息统一用当前界面语言解释。

### 4.3 检索、回答、交付分别定位

Deep分题搜索和补读已经存在，继续用。差答案必须区分召回没找到、证据未含条件、模型未采用、发布丢失、UI未展示；修对应层，不默认给每层加一个judge。

本轮不先换FAISS，不强制加reranker。只有标注案例显示相关资料召回不足、且开销可接受时，再对具体算法作对照。先在当前真实9B配置改善，不能只换昂贵模型掩盖代码短路。

## 5. 一键启动的最后一公里

### 5.1 打开已有和新建不能由“文件不存在”猜

现有Windows启动技术已成立。继续使用薄启动器，给工作区选择结果一个明确种类：open_existing / create_new / locate_missing。

登记路径失效：显示上次位置和最近使用时间，提供定位原目录、明确新建、退出。禁止自动mkdir+initialize。用户选的目录缺workspace.json或DB时显示“不是完整工作区”，可读取日志/检查备份，但不修改原文件。工作区有可核对的稳定ID；只维护必要注册元数据，不做全树hash。

显式新建则初始化一次。已有实例继续复用。模型离线仍进入设置/历史，不绕回安装流程。默认首次界面提供“已有资料”和“先体验示例”，示例使用独立标识，不默认改活动库。

### 5.2 发布程序不等于预装开发环境

构建脚本用显式解释器/工具参数或PATH工具发现，移除作者.venv绝对布局依赖。单个build命令在干净Windows目录准备官方嵌入式CPython、按锁导出并安装匹配依赖、构建React、打wheel、放入发行目录、编译现有启动器。缓存可以加速，但不充当未记录的必备步骤。

日常ESA.exe不访问PyPI，不要求Node，不下载模型。锁文件只需正常构建复现使用；不加入运行时源码指纹扫描。发布目录有一份版本、入口、平台、对应commit说明即可。

补原生目录选择、自动打开默认浏览器、物理中文输入法的真实检查；无法获得Windows环境时该项明确阻塞，不用Linux截图替代。

### 5.3 升级和恢复

升级程序保留原工作区。数据迁移按现有版本一次执行，失败则阻止继续写并给出恢复说明；不要求每次启动复制全库或扫描所有文档。退出/更新只处理自己的进程。恢复入口应明确“打开原数据”，不是“新建一个空目录试试”。

## 6. 前端继续完善，不再重新设计框架

现有三入口与单输入框保留。优先改有意义的交互：

- 资料库选择与真实绑定一致，空绑定显示“请选择资料库”，不要假装已选；已有无绑定会话可恢复。
- 运行与进度只属于当前会话；其他任务在角标/全局概览中说明，不绑架当前输入框。
- 历史服务器分页、搜索、重命名和归档；自动标题采用首轮问题短摘要即可，先用确定性截取不额外调用模型。
- 答案卡明确结论/限制/来源，业务卡明确当前状态/下一步。终止的历史事项收为“历史关联事项”，不误导用户继续办理。
- 重试按钮显示保留的模式和范围，知识库已变更则提示具体变化；同一回合重试不用重复用户消息。
- 错误给出可做动作：选择库、连接模型、等待排队、重新尝试；不要把嵌套dict渲染为[object Object]。
- 390px、键盘、焦点、中文composition、页面往返草稿、引用抽屉返回都属于交互基本质量，不以截图美观代替。

OpenAPI生成类型已经存在。日常API直接消费生成的请求/响应类型；工具结果用可辨别联合类型，不把所有内容退回JSONRecord再猜字段。Query缓存按对象ID和范围组织，导航卸载只取消客户端请求，不自动取消服务端run。

## 7. 长期数据与知识更新可用性

会话不只管理最近100条。使用游标分页与服务器搜索；确定排序和空结果行为，旧链接始终可读。必要时SQLite FTS支持正文搜索，第一版标题/预设文本查询足够，不为此换数据库。

知识库区分“当前已发布索引”和“正在构建的更新”。上传新资料时已有可用资料通常应继续可问，界面明确新增资料还在处理；新索引完整成功后切换。主动停用/撤销的文档应立即从新查询候选中过滤，不能借‘旧索引可用’继续暴露；旧历史引用可明确标历史或不可访问。失败则旧发布版本仍可用且显示更新失败，不能永久让整个库不可问。

从现有catalog/jobs/query和索引代次实现，不另外搭消息队列/分布式作业平台。作业错误可以按文档重试，统计真实处理数；取消请求与后台线程实际停止区别清楚，未停止时标‘取消中’，不要写成已经安全切换索引。此项要通过并发读/更新场景验证后才宣布完成。

## 8. 维护性：减少重复归属和格式猜测

继续当前模块化单体：bootstrap只装配、API只解析与调用、domain持有业务规则、coordinator持有回合/attempt、knowledge持有来源与答案、前端持有草稿与显示。

目前store约1700行、generation约1460行，不用按数值硬拆。优先沿真实调用职责提取，保留一次事务边界，不把一次提交拆成多次不一致写。压缩成一行/多分号并不等于简洁；公共流程正常格式化、有类型、有局部错误含义。

当前产品协议稳定后将多代understanding/writer/兼容分支隔离到legacy，不在默认产品入口中扫描或导入。不要一轮删除所有历史测试；只把与当前工厂不符的测试分组并标范围。

## 9. 改善可见性而不造监控平台

复用现有run/事件：记录检索耗时、生成耗时、工具次数、来源数量和结果类型；用户只看进展，开发详情展开后看必要日志。比较同一模型、同一数据、同类问题的before/after；没有基线不声称提升百分比。真正开销先从多余模型往返、密集schema和重复读源找，不增加无意义审查模型。
