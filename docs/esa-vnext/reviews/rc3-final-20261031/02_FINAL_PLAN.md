# 一次有终点的rc3收尾

## 范围与取舍

只完成F1知识恢复、F2历史可达、F3过期预览，整理对应页面和代码，完成现有关键旅程验证及教学映射。新框架、第三业务、向量库迁移、新解释模型研究、全仓格式化/拆分、整包哈希审计、另一套教学主计划均不在范围。

现有一键入口、React三入口、单输入框、原生工具循环、资料库、Fast/Deep、业务生命周期、SQLite事务/幂等继续保留。低频功能可以折叠，不可删除。

## W1：先确定本轮请求的真正依赖

修改重点：`service_desk/views.py`、`runtime/turn_coordinator.py`、`api/product_routes.py`，以及前端消费的TaskView/TurnDelivery。

目前TaskView可以继续提示借用缺日期，但当前Turn的knowledge恢复不能被这个提示否定。两者共享事实，不共享一项笼统“下一步”。

建议在已有投影中明确：

| 本轮未交付 | 整体事项缺字段 | 预期行为 |
|---|---|---|
| 只有知识 | 有/无 | 允许只补知识，任务侧可以非阻断提示待办理字段 |
| 只有预览 | 有 | 等待对应字段，不重试模型猜字段 |
| 预览＋知识 | 有 | 展示两项进度；允许查询/重试知识，预览等待补充 |
| 只有知识且已提交 | 不适用 | 读当前业务事实并回答，不重提交 |
| 无未交付 | 有历史缺字段 | 当前问答已完成，不因任务未办完伪造问答失败 |

选择顺序还要保留run占用、待核对用户修改等真正不能并发的状态。恢复复用原问题/模式/知识范围，读取当前业务事实；不重放已应用输入。

不新增持久化的第三套工作流状态，不新增关键词意图分类器，不把语义完备交给一轮额外judge。结果来自现有request brief、pending项和真实工具结果。

## W2：详情查询与列表分页彻底分离

`QueryOperations`新增或复用按id读取的单一函数；产品答案路由直接调用，不能过滤最近列表。继续经过原DTO和来源有效性提示，不将停用文档偷偷替换成新内容，不扩大可读身份范围。

事项列表复用已有会话页设计：返回items、next_cursor等明确结构；前端可加载更多并由服务器搜索。排序使用稳定二元键（如创建顺序＋ID），刷新新记录时不能跳页/重叠。若当前存储已有稳定rowid且符合本版本使用方式，也可先使用该键；不为了游标抽象新建通用查询框架。

只选择一种API接入方案：新增分页路由并更新前端，旧列表短期仅保兼容；或完成一次受控契约升级。不要长时间保留两种各自独立的事实列表。

至少检验55条及同时间戳记录、空结果、旧答案直达、搜索跨页。不要用“上限改为5000”掩盖问题。

## W3：当前可操作性来自同一份预览信息

预览生成时已有expires_at、facts_revision及依赖绑定，不需要增加签名链或源码哈希。

读模型根据能够确定的过期/修订情况标注current/expired/stale，can_submit与主按钮使用同一个结果。仅GET不做业务写入、不反复调用模型。预览正文可留作参考但明确已失效。

前端使用服务器给出的时间信息，在已知截止点或重新获得焦点时刷新当前事项；定时器随事项切换清理，不全局频繁轮询所有任务。真正提交前保留事务中的确认校验，避免在GET与POST间变更造成错误。

文案：`预览已过期，参数已保留。重新生成后再确认。` 主动作“重新生成预览”，不能退回模糊的红色报错或继续显示提交按钮。

## W4：只整理受影响的页面状态

沿用rc3字体、绿色强调色、三入口、抽屉和单输入框。本轮不是新设计系统工程。

1. 助理回复区展示本轮成果与恢复动作；任务抽屉展示办理步骤，不互相抢夺“下一步”。知识错误不把用户强制送回日期表单。
2. 正常缺字段保持现有自动展开/聚焦。主操作按当前意图区分“补充”“选择”“重试解释”“重新生成”，同一恢复行为不在三个地方重复报错。
3. 我的事项支持跨页查找；来源/答案详情可打开历史记录。移动版仍需可进入历史，不能只用CSS隐藏后无替代入口。
4. 过期预览展示参考内容和重新生成入口；历史回执与当前单据状态继续分开。
5. 成功保存的参数继续由mutation返回值更新缓存；后续步骤失败不要回滚已保存事实。服务器缓存、未保存草稿、展开状态保持既有边界。
6. 仅针对涉及组件收敛重复状态/错误映射，使用现有Query键定向刷新。不要删正确的业务if以追求更少行数。

视觉只做一次整体验收调整：1440、1024、390px，正常回复/知识失败/补字段/候选/过期预览/历史列表。无横向溢出、重复输入框、遮挡主按钮；关键说明能读、Dialog焦点正常。没有真实截图时不写“美化已验收”。
