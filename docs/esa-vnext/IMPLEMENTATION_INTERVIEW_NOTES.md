# 实施中真实遇到的问题：面试记录

本文件随实际实施补充；未验证的判断不写成结论。产品进度仍只以 STATUS.md 为准。

## 1. 模型不可用，为什么连网页也打不开？

- **实际现象**：2026-10-30 按现有 `tools/launch_local.py` 启动离线 TEST 入口，进程在 `dual_track_worker.py::prepare` 调用 Ollama `/api/tags` 时抛出 `httpx.ConnectError / WinError 10061`，网页没有启动。
- **定位**：启动路径在创建 Web 服务之前就同步检查模型，错误被一路抛到 launcher；离线模式也依赖这个步骤。模型服务后来可连接，不改变该启动耦合缺陷。
- **处理**：现有 `app.main.create_app` 新增工作台模式；其 lifespan 只启动持久存储和 HTTP 客户端，不加载模型、索引或生成预热。模型状态改为独立的 `/api/status` 能力查询。
- **当前验证**：`python -m app.cli init --sample --data-dir .private/esa-vnext` 创建固定目录；`doctor` 能返回真实已安装模型元信息，未发送生成请求。修复下面的中间件问题后，实际 Edge 浏览器把 endpoint 临时设为未监听端口，确认页面仍可用、设置能刷新保留，再恢复原 endpoint。截图和检查记录在本地数据目录 logs/M1_BROWSER.json 等文件。
- **面试口述**：最开始我把依赖检查放在服务启动前，导致模型暂时不可用时整个应用都起不来。后来把进程存活和功能就绪拆开，先让设置、历史和资料列表可访问，再按具体操作判断模型能力是否可用。

## 2. 服务已经启动，为什么访问设置仍是 503？

- **实际现象**：新入口在 8740 启动成功，`/health/live` 可用，但首页、设置、状态和历史返回 503。实际响应错误码为 `identity_unavailable`。
- **定位**：不是页面或路由没注册，而是沿用的 `TrustedIdentityMiddleware` 对所有非健康检查请求先做身份可用性检查，新工作台的静态页面和本地设置尚未到路由就被拦住。
- **处理**：仅在工作台模式下，将其自有 `/api/`、静态资源和首页交给本地访问边界；原文档/操作员接口继续走 bearer 身份中间件。本地写操作检查 loopback、Host、Origin 和自定义请求头，不开放远程部署。
- **验证**：3 项真实应用路径的程序回归先因 503 失败，修正后通过；连同原身份 API 共 37 项通过。覆盖缺模型/身份时页面可用、原受保护 API 未公开、外部 Origin 和无请求头写操作被拒绝，以及同库重启；实际浏览器检查也通过。这证明启动和访问边界，不代表知识或业务任务已经完成。
- **面试口述**：这次问题说明“进程起来了”不等于“用户能使用”。我从真实 HTTP 错误体定位到中间件，而不是继续改前端。修复时明确哪些是可访问的本地产品页面，哪些仍需要业务身份，并用两边的请求验证边界。

## 3. 模型已经答对，为什么用户仍收到超时？

- **实际现象**：首条新工作台实时问答中，BGE建索引完成，9B的原始响应包含资格、1至14天、开始日期、单一未关闭申请及待审批说明；chat约64.6秒返回。最终HTTP却交付 system / cancelled_or_deadline。原件：本地 logs/M2_KNOWLEDGE_LIVE.json 和 app.sqlite3/model_calls。
- **根因**：新知识服务的内层预算是240秒，但继承了旧HTTP中间件的短请求Context；runner取两者最小期限。不是模型没有返回，也不能靠更改完成标签解决。
- **处理**：知识操作变成持久run，短HTTP只创建/查询run，SSE展示进展；后台有独立的有界Context，取消与进程中断单独记录。旧HTTP期限保留。
- **验证边界**：同一问题的针对性真实复验能交付正文，不再被外层期限丢掉；该次答案仍为partial，存在来源单元组合/选择问题，尚不等于知识质量验收通过。
- **面试口述**：我遇到过“模型成功，产品失败”：内外层超时不一致，结果生成完却在发布前被判过期。我把长操作的生命周期从浏览器请求里移出，持久保存进度和结果，同时保留每次请求、run和取消保护。

## 4. 为什么改几次日期后，正常申请就不能再预览？

- **源码证据**：已有Store把每任务历史预览总数限制为3，工具/模型总调用也绑定整条任务寿命；新信息会消耗永久额度，正常改期最终被BUDGET_EXCEEDED拦住。
- **处理**：有效且依赖未变的同版本预览复用；真正修改使旧预览失效并生成新预览。新产品run保留8步和工具上限，历史调用累计留存，不再用任务终身计数阻断正常修改。参数保存增加事务内facts_revision校验，缺省不改、显式null清空。
- **验证**：实际SQLite程序回归连续6次改期仍可预览；旧确认被拒、当前确认生成唯一PENDING_APPROVAL、重复提交与重启读回一致。这里是程序测试；真实模型/UI的完整旅程单独记录。
- **面试口述**：我区分了业务任务寿命和单次Agent运行预算。预算防止一次推理空转，不应该把用户正常修改日期永久锁死；权限和确认则绑定当前参数版本，参数一变就要重新预览和确认。

真实补充：随后实际9B通过native tool_calls选择了规则、库存、本人申请和预览；同一UI任务改期后拒绝旧确认，当前精确确认生成唯一待审批工单，刷新读回通过。见本地 logs/M4_LIVE_UI.json、M4_LIVE_RECEIPT.png 及数据库原始事件。这不是预设工具顺序的策略测试。

## 5. 结构化输出合法，为什么日期却被塞进了用途？

- **实际现象**：一次真实自然补充返回合法JSON，但changes只有purpose，内容混入日期和操作；sources却用了start_date、end_date等另一组字段名。宿主以UNBOUND_PARAMETER_UPDATE拒绝更新，数据库没有被错误修改。
- **根因**：changes与任意键sources是两份独立表示，采样schema没有把“哪个字段、值、原文”绑定在一个对象中；模型结构合法仍可能语义错位。
- **处理**：统一为updates数组，每项是枚举field、value、exact quote；字段不重复，原文片段必须存在，用途必须来自其片段。日期交给既有业务类型校验。模型不能扩大操作上限。
- **实测**：同一自然请求的有区分复验，正确保存2026-11-01、2026-11-03和“异地会议”，原READ_ONLY保留；后续真实只读分支读到已有工单，工单数1→1。见logs/M4_SHARED_BRANCH_20261029T182938.json。
- **面试口述**：JSON合法只解决语法，不能保证业务字段正确。我把两份容易脱节的字典收敛成字段、值和来源的单条记录，由宿主检查来源与版本，再交给普通业务代码执行。

## 6. 正文已经完整，为什么还说“尚未核验”？

- **实际证据**：双入口实时答案已包含资格、期限、日期、申请数量、待审批和押金说明，source-unit绑定完整；模型对状态问题却返回“主体/属性/条件都匹配，但evidence_insufficient”。还发现旧关键词分支凭另一句“什么”扩写出未被要求的申请材料诉求。
- **已处理**：移除这些扩写分支；来源单位使用宿主ID选择，避免模型把两个受保护完整单位拼成一个无法绑定的关键断言。正文已经不再丢失。
- **修后实测**：默认知识需要保留整个原问题，避免标点拆分漏掉第一组条件；清晰区分“已回答一个否定问题”与“业务已批准”。d25b4048知识代码的有限真实双入口复验均answered，资格、期限、日期、申请数量、待审批及押金说明均保留；见logs/M2_KNOWLEDGE_PAIR_20261029T184116.json。不是直接把partial改成answered，而是保留真实模型判定、宿主引用核验和最终正文一致性检查。

## 7. 为什么开发目录能跑，从提交导出的副本却启动失败？

- **真实复现**：M6从d25b4048只导出app与安装描述，以 `python -I -S` 禁用editable路径钩子、只复用第三方依赖启动。实际抛出 `ModuleNotFoundError: app.workbench_knowledge`。
- **原因**：知识模块在本机是未跟踪文件，阶段暂存时漏掉了。普通工作目录测试和直接从工作目录打wheel都会把它带上，因此之前能运行并不能证明提交自包含。
- **修复**：将实际模块纳入当前分支，保留独立源码探针；从提交再次导出并启动。此处是代码/资源隔离验证，第三方依赖仍使用已安装版本，不冒称验证了全新系统安装。
- **面试口述**：我把发布验证从“在原目录跑一遍”改成“只取提交中的代码，隔离editable导入后启动”，发现了漏提交文件。这个问题也让我明确区分源码自包含、依赖安装和功能验收。

## 8. 干净环境网页能开，为什么第一次进Agent却缺依赖？

- **实际复现**：独立环境按锁安装后，页面探针通过；显式导入工具循环却报 `ModuleNotFoundError: langgraph.checkpoint.sqlite`。
- **定位**：`app.agent_runtime.__init__` 自动导入历史durable_orchestrator、evaluation和MCP；新薄循环本身不用这些模块，却被包初始化带上旧栈。原开发环境装过旧依赖，掩盖了问题。
- **处理**：旧公共导出改成按需加载，显式调用旧接口时仍保留；LangGraph移到legacy可选依赖。独立探针现在还检查薄Agent导入且旧图/评测未被加载。
- **验证边界**：此处验证安装和依赖边界，不把“可以import”当作真实模型任务成功；真实模型轨迹仍单独保存在数据库和本地记录中。
- **面试口述**：我不只是补装一个缺失包，而是检查为什么默认功能需要它。最后消除了模块初始化的隐式依赖，让日常入口只加载实际使用的能力，历史实现仍可显式使用。

## 9. 用户给出办理日期后，为什么反而“找不到制度”？

- **实际复现**：知识转任务的真实界面旅程中，问题带有借用日期和用途。检索、Guard均拿到两份准入文档，最终却在生成前返回not_found；数据库没有chat发送，因此不是9B模型没有理解。
- **根因**：旧抽取式路径把问题中的四位年份当成正文必须出现的版本锚点。用户的办理日期被误当成制度版本；检索候选过滤又被当作“所问内容不存在”。
- **机制改动**：共享KnowledgeService复用已有语义need/来源单位/发布契约，原问题整体保留。检索负责提供通过准入的候选，生成返回逐need关系，唯一publisher在最终正文上重查来源绑定和覆盖；没有新增日期或题号分支，也未把所有候选直接当成正确答案。旧抽取接口保留其原合同。
- **验证**：58项相关离线回归通过，包含未知条件不能仅凭来源绑定宣称完整的负例。原失败输入再走真实UI，完成知识回答→用户选择范围并提取原问题参数→选择实际设备→预览→改期清确认→旧确认409→当前确认→幂等读回。TEST任务`8f868cae456244bba31cb0a995e6ef11`；原件在独立demo-validation目录的J10记录及数据库。没有重放旧答案。
- **面试口述**：我沿调用账本发现生成模型根本没被调用，再定位到检索后的旧锚点规则。修复的是“候选发现”和“答案完成”混为一谈的问题，而不是给这一句话加例外。最后同时检查了答案正文、真实工具记录和数据库，避免只看完成状态。

### 后续没有掩盖的第二个缺陷

这条J10业务闭环通过，但知识结果当时仍为partial，不能说整体质量通过。检查同一份原始响应发现：宿主从原文恢复了模型正文中已经写出的片段，却没有保留已有的唯一need关联，最终发布又删除它。已用该真实合成响应穿过完整打包、解析、映射与发布复现，修复仅保留无歧义的既有关联；多个need归属不明确时仍不猜，unknown或缺少判断也不升级。相关44项离线回归通过。随后相同输入真实双入口均answered，六类所问内容完整保留；原件`demo-validation/logs/KNOWLEDGE_HANDOFF_PAIR_20261029T195549.json`。这是有限场景结果，不是通用准确率或追平main的结论。

## 10. 为什么诊断和重复启动会干扰正在跑的任务？

- **发现**：重复启动的离线真实路径未拒绝同目录的第二实例；旧启动恢复会将running改为interrupted。doctor原来也调用完整Workspace.start，而非只读检查。
- **修复**：数据目录使用操作系统文件锁，先取得所有权再恢复。崩溃由OS释放锁，不靠删锁文件。doctor只读配置、SQLite和本地模型标签，不执行恢复。
- **证据**：红测试实际报DID NOT RAISE；修后同目录第二实例拒绝、原running行不变；另起的测试子进程异常退出后重新取锁成功，doctor旁路也不改运行记录。没有模型调用。
- **面试口述**：恢复逻辑本身没错，但它必须有唯一所有者。我把“检查状态”和“启动并恢复”分开，避免诊断工具反而改变业务状态。

## 11. 切换任务为何还会看到旧的确认？

- **实际复现**：浏览器切换到仅预览任务时，旧任务的提交控件仍留到网络读取结束，首轮检查失败。异步响应还可能按错误顺序回写界面。
- **修复**：点击切换时立即清确认并移除旧表单，显示加载状态；每次选择有递增版本，旧响应不能替换新选择。权限仍由服务器精确确认和执行上限检查。
- **证据**：浏览器延迟真实API响应，检查旧响应不能覆盖新任务；切换/改期清确认、仅预览宿主拒绝提交、长文本窄屏和脚本文本均通过。这里是PROGRAM_FIXTURE，不宣称模型成功。
- **面试口述**：这不是多隐藏一个按钮的问题，而是异步响应属于哪一次选择。前端负责让用户看对当前任务，后端继续保护实际参数和提交。

## 12. 第二个业务怎样避免复制一套Agent和事务？

- **实际工程问题**：原公共接口默认借用字段、借用规则、loan命令前缀和待审批状态，直接加报修会串业务。
- **实现**：从实际借用路径抽出固定的两个服务定义，领域字段、读取/校验与状态不同；任务、表单、原生工具循环、proposal、confirmation、command事务和读回复用。报修用独立业务表，但共用命令账本，不改借用维修资格。
- **实测**：真实9B/UI报修旅程5次chat；描述和影响程度自然修改，旧确认409，新确认只落一张OPEN单，重试回同一回执。借用工单、库存、资格和规则前后完全未变。
- **取舍**：缓存可用不等于模型一定少调用。另一只读检查里读取类别3→1，但chat2→2；未宣称整体更快。文档嵌入缓存的2→0请求是另一项独立测量，不能混成Agent提速。
- **面试口述**：我先复用已经正确的交易生命周期，再把真正不同的领域规则放进适配器。扩展后用两个业务库的前后状态证明没有交叉污染，不只是看界面多了一个选项。

## 13. 打包预算和真正发送的参数为什么要一起检查？

- **真实证据**：保存的RAG请求options.num_predict为1800，而打包器实际只预留1024。离线经过真正sync_chat回调和HTTP序列化的红测试得到1800 != 1024。
- **修复**：传输的默认输出和上下文长度复用既有serving_chat常量，与打包器同源；native工具选择600、字段理解500等显式小额度不变。没有提高预算掩盖问题。
- **边界**：这是已证实的契约不一致；并未声称之前所有失败都由它引起。修后需要在冻结候选上检查真实发送与正常输出，结果见STATUS。
- **面试口述**：只看配置文件不够，我比较了打包器预留和账本里的实际请求，再用真实适配器复现。最后消除了两个默认值，让估算与执行共享一个定义。

## 14. 正文完整，为什么跨文档比较仍然显示partial？

- **原件与复现**：955bf690的真实双入口比较都拿到两份来源，逐need语义关系和正文绑定完整，却被标partial。保存的同一回复通过真实解析/映射/发布函数回放，红测试重现“2 required aspects”警告。
- **根因**：旧检索方面检查要求实体名称出现在每条引文里；来源原句通常只说“每次预订不得超过2小时”。它把词法锚点当成第二套语义完成结论，与逐need发布器冲突。
- **修复**：语义任务保留词法统计作诊断，完成只由既有发布器检查已交付断言与绑定关系。上游预算partial、未知/缺失语义关系、来源保护仍不能被提升为完整；旧词法模式维持原契约。
- **证据边界**：原件回放正例及未知/缺失关系、上游partial负例通过。670fdb66上的新真实双入口均保留两份来源和全部必要内容，answered与正文一致；原partial记录仍保留。不能把这一个修复说成普遍准确率提升。
- **面试口述**：我没有简单把partial改成answered，而是沿trace找到两层在回答不同的问题。检索锚点用于找资料，最终完成判断必须检查用户问题与实际交付内容，不能让两套判断互相打架。

## 15. 为什么作者机器通过，独立安装却失败？

- **真实错误**：独立Windows虚拟环境测试出现ZoneInfoNotFoundError: Asia/Shanghai。作者环境已有tzdata，默认依赖未声明；另有一项A1测试依赖的仓库内HTTP helper没有进入源码导出。
- **修复**：把已有锁中的tzdata固定为直接依赖，导出纳入该最小helper。没有改成服务器本地日期、跳过业务测试或依赖作者环境。
- **验证**：失败JUnit保留；最终从提交导出的源码、独立venv、显式本地pythonpath重跑，同一组断言结果见STATUS。
- **面试口述**：干净环境不是再执行一遍作者目录里的测试。要隔离editable路径和父目录配置，才能发现隐式依赖与漏打包。这个问题说明可复现安装本身就是工程验收的一部分。

## 16. “离线测试”为什么仍可能误触真实模型？

- **实际失败**：期限检查用1ms期限加sleep(10ms)，Windows计时粒度导致一次未过期，测试触达本地HTTP并超时。该临时TEST库的1条ERROR发送原件另存，没有隐去或算作成功。
- **处理**：测试使用可控单调时钟推进到明确过期，并给模型客户端装MockTransport，任何错误发送立即断言失败。真实send、期限拒绝和数据库0行断言仍都执行。
- **结论**：修复的是不确定的测试安排与测试隔离，不声称发现了生产期限绕过。计入额外1次尝试；产品原账本不改写。
- **面试口述**：测试超时逻辑不能靠真实sleep碰运气，更不能默认开发机没有模型服务。我让时间和外部I/O都可控，才知道保护条件真的执行过。

## 17. 为什么“run已取消”，事项却仍无法继续？（0.3升级）

- **本轮复现**：三个真实代码路径红测分别得到asset_id KeyError、知识追问NO_WRITE_GOAL、run取消后task仍有active_run_id。全部为脚本模型+真实Store/SQLite，未冒充实时模型。
- **共同责任问题**：服务字段schema与全局补问词典分离；所有消息都先当业务字段修改；run终态和task占用分别收尾，而CancelledError不属于Exception。
- **修复**：字段schema供表单与补问共用；知识消息分流；既有运行器使用RunLifecycle统一释放自身nonce/fence，并在发终态事件前完成清理。取消输入保留原文、标未应用，继续不靠重启。
- **验证**：21项相关检查通过，包含完整借用/报修、取消后继续、取消消息释放、旧run不能清新owner。新UI/模型旅程仍在后续升级中验证，不能提前宣称完整会话已完成。
- **面试口述**：我发现取消的不只是协程，还要结束它拥有的业务运行状态。清理必须核对所有权，并在通知前端结束之前完成，否则页面看似停止，下一次请求仍被旧占用拒绝。
